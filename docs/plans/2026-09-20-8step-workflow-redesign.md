## 0. 上游（原版 straditize）教程对照

上游 12 步：`载入 → 选数据区 → 建 reader → 分列 → 列名 → 去伪影 → 数字化 → 样品层位 → Y轴标定 → X轴标定 → 元数据 → 完成`
（源码 `straditize/straditize/widgets/tutorial/hoya_del_castillo.py`，正文 `tutorial/hoya-del-castillo/*.rst`）

### 0.1 采纳

| 上游做法 | 我们的处理 |
| --- | --- |
| **`reader`（列组）≡ 命名 ROI**：Charcoal / Columns 1–26 / Column 27 三个 reader，各自类型 + X 标度 | **ROI = 列组 + 取数窗口 + 导出表名**。三者是同一抽象；我们的模型是其严格超集（上游 reader 不含取数窗口） |
| **同组列常共享 X 标度**：上游 Hoya 图 27 列共用 `xaxis_data = [0, 40]`，教程原文 "they all have the same scaling… enough to perform the above steps just for one of the columns" | ⚠️ **是常见情形，不是不变量**（实测 `type2_exaggeration_bell.png` 逐列刻度区间数 1~7 不等，满刻度值 10~70 各异）。因此：**事实源永远是逐列的 `(x₁,v₁),(x₂,v₂)`**；ROI 级只是**用户显式声明的批量便捷入口**，**严禁据此推断"应该相同"** |
| **列组共享图形类型**：整图默认 `area`，浓度列 `new_child_for_cols([27], 'line')` | 同上，ROI 级默认 + 单列覆盖 |
| **去线 = 候选 → 勾选 → 一次 Apply** | 清理加"候选线"层：结构化线对象可单条取消，Apply 原子生效 |
| **两个独立旋钮**：`line_fraction`（横 0.75 / 竖 0.30）与 `min_lw…max_lw`（竖线严格 ≤2px） | 取代原"弱/中/强"耦合档位 |
| **标定 mark 是一等对象**：可拖拽重定位、右键删除；拖拽时按 Shift 松手不弹窗（只挪位置不改值） | 补：mark 的位置与值都可事后修改 |
| **样品层位可视化编辑**：自动找（列极值）→ 每层一条水平线，左键拖 / 右键删 / Shift+左键加 | 补：第 7 步拆出「7b 采样层位」，接后端已有的 `extract_horizon_consensus` |
| **"informative features" 语义**：去掉的是"对读者仍有信息量、对数字化有干扰"的要素，**不是纠错** | 清理必须可逆、可复核、不破坏原图；原图永不改写 |
| **上游明说用户常在 Photoshop 预处理** | 我们的**矩形/多边形排除区**填的正是这个缺口（上游没有） |

### 0.2 不采纳

| 上游做法 | 理由 |
| --- | --- |
| 数字化 → 样品 → **最后才标定** | 顺序不影响正确性（数字化是纯几何，标定只改变解释），但标定早做能让深度标尺全程可用，体验更好 |
| **弹小对话框**输入标定值 | 用户明确要求改为左栏直接填；弹窗不可反复修正 |
| `reader` 支持**嵌套子 reader 树** | 复杂度不值；ROI 一层列组足够（ROI 内不再分组） |
| 分列 → **列名** → 去线的先后 | 列名并入分列步骤（第 5 步）；去线见 §3.3 |

## 1. 目标步骤机

```
1 载入 → 2 ROI(命名/多ROI) → 3 Y轴标定 → 4 清理 → 5 分列 → 6 标定列 → 7 拐点与采样层位 → 8 校验
```

**与现行对照**

| 现行 | 新 | 变化 |
| --- | --- | --- |
| S1 载入 | 1 载入 | — |
| S2 ROI | 2 ROI | **只留框选与命名**，深度输入与去线移出 |
| — | **3 Y 轴标定** | 从 S4 拆出，升为独立步骤 |
| — | **4 清理** | 从 S2 拆出，扩为四类线 + 排除区 + 候选线列表 |
| S3 分列 | 5 分列 | 后移一位（清理前置）；并入列名/OCR |
| S4 标尺 | 6 标定列 | 只留**组级**（ROI 级）标度/形态 + 单列覆盖 |
| S5 拐点 | 7 拐点**与采样层位** | **新增 7b 采样层位**（上游 `SamplesPage`，导出的行轴） |
| S6 校验 | 8 校验 | 门禁语义重写（见 §6） |
| S7 导出 | — | **删除**；导出由顶栏总出口承担，导出对话框内改为"就绪清单" |

### 1.1 为什么清理必须在分列之前

`detect_columns` 的输入就是 ROI 内的墨迹掩膜。若先分列再清理，只有两个结局：

- 分列时 ROI 里还有文字/杂记 → 切出幽灵列，清理后列仍在，必须重分列；
- 或清理只作用于拐点提取 → **分列看到的墨迹 ≠ 数字化看到的墨迹**，正是上一轮刚消灭的那类双掩膜缺陷。

依赖链因此固定为：图 → 取数窗 → 语义轴 → **掩膜** → 列 → 每列标度 → 数字化(掩膜+标度) → 校验。

3 与 4 互不依赖，可互换；把 Y 标定放前面是因为标定后深度标尺即可绘制，清理时有坐标系可定位。

## 2. 数据模型

```ts
interface DataRoi {
  id: string;
  name: string;            // 默认 "pollen"，唯一，校验规则见 §4
  composition: boolean;    // 默认 true：各层位总和应 ≤ 100%
  xMin: number; xMax: number;
  yMin: number; yMax: number;
  visible: boolean;
  /** 组级批量入口：ROI 内各列"一键继承"用的默认值。
   *  ⚠️ 这只是省事的批量赋值入口，**不是事实源** ——
   *  不同列的刻度区间值（5 vs 10）与满刻度值（30 / 50 / 70）可以合法地各不相同，
   *  因此严禁由它推断"各列应当相同"（实测反例见 §5.3）。
   *  事实源永远是逐列的两个刻度端点 (x₁,v₁),(x₂,v₂)。 */
  defaults: {
    plotType: 'area' | 'bar' | 'line' | 'symbol';
    startValue: number;    // 批量赋值的起点读数
    tickValue: number;     // 批量赋值的满刻度读数
    unit: string;          // '%' | '粒/g' | ...
    scaleType: 'linear' | 'log';
    exaggerationMult: number | null;   // null = 无局部放大
  };
}

interface Column {
  ...现有字段;
  roiId: string;
  /** 该列自己的两个 X 刻度端点（**事实源**）：像素 + 读数 */
  xTicks: [{ px: number; value: number }, { px: number; value: number }] | null;
  /** null = 本列的具体值来自 defaults 的批量赋值；非 null = 该列单独指定 */
  override: Partial<DataRoi['defaults']> | null;
}

interface DiagramData {
  rois: DataRoi[];
  activeRoiId: string;
  columns: Column[];        // 扁平列表，每列带 roiId
  calibration: DepthCalibration;   // 全局唯一，多 ROI 共享
  exclusionRegions: ExclusionRegion[];
  lineRemoval: LineRemovalState;    // 按 ROI 分组，见 §3
  ...
}
```

### 2.1 关键决策与理由

- **`Column.roiId` 用显式字段**，不用"列 x 落在哪个 ROI 内"推断：ROI 纵向堆叠（共用 x 范围）时后者歧义。
- **标度的事实源是逐列的两个刻度端点 `(x₁,v₁),(x₂,v₂)`**，不是"每列一个满刻度值"。
  ROI 级 `defaults` 只是**用户显式声明的批量赋值入口**：它省去逐列录入，但**不得被当作
  "各列应当相同"的证据**——实测反例（§5.3）：同一张图的列刻度区间数 1~7 不等、
  满刻度值 10~70 各异，且区间值本身也可能逐列不同（5 vs 10）。
- **X 标定的首选路径是「几何检测刻度线 + 用户看图读出两个数字」**（§5.3.1），
  不是 OCR 读刻度数字（该路径已决策**不引入**），也不是让用户逐列手填。
- **`calibration` 全局唯一**：Y 轴是整幅图的属性，不随 ROI 变（用户明确要求"多 ROI 共享 Y 轴"）。
  ROI 的 `yMin/yMax` 是**取数范围**，可以各自不同——这正是上一轮建立的"区域 ≠ 标尺"。
- **`composition` 是布尔而非三值枚举**：实际只有一条计算需要它（`Σ ≤ 100%` 约束是否适用）。
  导出单位用 ROI `defaults.unit` 或列 `unit`；`proxy`（pollen/charcoal）属于论文元数据，不属于 ROI。
  **不从列单位推导**：混合 ROI 会被静默误判，而把百分比规则套到浓度表上正是项目禁止的静默错配。
- **采样层位（`sampleDepths`）是一等数据**：它是导出矩阵的**行轴**（上游 `SamplesPage`）。
  来源可以是后端自动识别（`extract_horizon_consensus`，已实现但前端从未接）、Excel 粘贴、或图上手绘。
- **删除 `data.panels` / `DiagramPanel`**：现仅在 `Inspector.ts:886` 被"追加子有效区"用来造一个后端不知道的假面板。
  由 `rois` 取代。

### 2.2 后端对应

- `self.rois: list[dict]`、`columns[i]["roi_id"]`；
- `_roi_box(roi_id)`、`_roi_mask(roi_id)`、`_extraction_mask(roi_id)`；
- 线掩膜与排除区**按 ROI 存**（一个 bool 数组 2339×1654 ≈ 3.9 MB，几个 ROI 无压力）；
  合并成单一全局掩膜在 ROI 重叠时会互相污染，不做；
- `detectColumns(roi_id)` 只替换该 ROI 的列；`digitize(col_index)` **签名不变**（全局索引），
  内部按列的 `roiId` 取掩膜与 ROI 围栏；
- 持久化：`straditize.json` 增加 `rois` / `exclusion_regions`；`line_removal` 改为按 ROI 分组。

### 2.3 前景分层：exaggeration 必须显式分层（实测结论，之前从未验证）

**实测**（`type2_exaggeration_bell.png`，Bell 2018 风格真图，30 列，四层灰度）：

| 层 | 颜色 | 灰度 | 全局 otsu=159 下 |
| --- | --- | --- | --- |
| 真绿（真实值 ×1） | `[34,139,34]` | **95.6** | 判为前景 ✅ |
| 放绿（放大 ×N） | `[143,197,143]` | **174.7** | 判为背景 ✅ |
| 真黄（真实值 ×1） | `[238,201,0]` | **189.1** | **判为背景 ❌** |
| 放黄（放大 ×N） | `[247,228,126]` | **222.1** | 判为背景 ✅ |

**不可能性**：要保留真黄填充需 `thr ≥ 189.1`，要排除放绿需 `thr < 174.7` → **无解**。
因为排序把"**另一族的放大层**"夹在"**本族的真实层**"之前。

**裕度**：放绿距 otsu 仅 **15.7** 灰度；真黄填充距 otsu 仅 **30.1** 灰度。

**当前为什么没炸**：黄色列的填充被判背景，但**更深的描边（灰度约 129）把轮廓救了回来**
（实测 col16 前景 3368 px vs 填充 10388 px，前景只等于描边）；`area` reader 读最右墨迹＝轮廓右缘，
所以值**仍对**。—— 这是巧合，不是设计。

**两个具体崩法**：

1. 阈值上移 16 个灰度 → 放大层混入 → **绿色列的值放大 N 倍**；
2. 图若是**无描边纯填充**风格 → 黄色列**整列无数据**，导出会把它写成"该属种未出现"，
   即**把未观测写成确定**（黑名单第 5 条）。

**设计结论**：

- **禁止**用单一全局阈值处理多色系 + 深浅双层的图；
- 改为 **按色相（色系）分组 → 每组内按双峰/聚类定阈 → 显式分成"真实层 / 放大层"两层**；
- `exaggerationMult` 是**列级属性**（模型已有字段），必须：
  - 由用户确认或由图层分离结果推断后**明确标注来源**（不得静默猜倍数）；
  - 进导出元数据，供审稿审计（倍数搞反是**系统性 5–10× 偏差且图上完全正常**）；
  - 与 §6.3 的 `per_column_max` 单列越界告警**联动**——倍数搞反正是该告警的典型成因。

**这条必须先出探针单**（任务单 `T00-a`，通过后才开 `T12`），不得直接写实现契约。

## 3. 清理（第 4 步，常驻面板）：四类线 + 候选列表 + 排除区

### 3.1 四类线按**几何判据**定义（不按名字）

上游把"每列起始的竖直虚线"就叫 **y-axes**（`remove-lines.rst`：
"vertical, dashed lines at each column start (**the y-axes for each column**)"）。
为避免命名歧义，四类一律按几何定义：

| 类 | 判据 | 典型 | 参照系 |
| --- | --- | --- | --- |
| **A 贯穿横线** | 跨 ≥90% ROI 宽、够薄 | zone 分隔线、深度网格、顶/底框 | ROI |
| **B 贯穿竖线** | 跨 ≥90% ROI 高、够薄 | 左/右框线、分区竖线 | ROI |
| **C 列内竖线** | 贴某列起点 ±δ、跨 ≥60% **该列**高 | **每列 y-axes**（列基线虚线） | **列** |
| **D 列内横线** | 跨 ≥60% **该列**宽、贴近列底 | 每列 x-axes 基线 | **列** |

**两个独立旋钮**（取代原"弱/中/强"耦合档位，上游做法）：
- `line_fraction`：线要跨过的比例（横默认 0.75 / 竖 0.30）；
- `line_width_min … line_width_max`：线宽范围。**竖线必须严格限宽 ≤2px**（上游教程值），
  否则会把列基线（数据的一部分）当线删掉；`line_width_max` 由复选框启用。

### 3.2 候选线是**结构化对象**，不是像素

上游流程是"点按钮 → 候选标红 → 可编辑选择 → Remove"。
我们采纳：

1. 检测后左栏列出**候选线清单**（每条的像素位置、跨度、实测线宽）；
2. 用户在画布上点选/取消单条候选（或左栏勾选）；
3. **Apply** 才原子生效（一条 Command 入撤销栈）。

像素级笔刷（`K`，上一轮已做）**退为兜底**：处理算法检不出的（虚线网格）与非线状杂记。

### 3.3 清理是**常驻面板**，不是一次性闸门

C/D 两类以"列"为参照系，**分列之后才存在**；而 A/B 与排除区在第 4 步就可用。
因此清理**不能**是一次性步骤：

| 时机 | 可用 |
| --- | --- |
| 第 4 步起 | A/B 贯穿线、排除区、笔刷 |
| **分列之后（随时回访）** | C/D 列内线自动启用（列清单已存在） |

**任何清理变更** → 标记 `columnsStale = true` → 右栏出现
「⚠ 掩膜已变，分列可能已失效 [重新分列]」**一键按钮（提示而非强制）**。

这样"清理在分列前"与"清理在分列后"两种诉求同时成立，只是管的线不同类。

### 3.4 排除区（矩形 / 多边形）

上游明说用户通常在 **Photoshop** 里预处理掉这些杂记（"You can do this in an
external image editing software (e.g. Photoshop)"）。我们的排除区填的正是这个缺口。

它与线掩膜编辑的是**不同对象**：线掩膜去"细线"，排除区声明"这块整体没有数据"。

- 必须**用户显式绘制**（矩形拖拽 / 多边形逐点点击后双击闭合），不得自动推断；
- 可列出、可删除、可拖动顶点修改；
- **常显**：在清理步骤用斜纹半透明绘制，不需要按 B；
- B 键叠加层由两色扩为**三色 / 四色**：
  白=保留墨迹 / 红=剔除的线 / **黄=列内线（C/D）** / 灰斜纹=排除区。

### 3.5 语义边界：清理不是纠错

上游称之为 "informative features … **that are informative for the reader**"。
即：**去掉的是"对人仍有信息量、对数字化有干扰"的要素**。
因此：清理必须可逆、可复核、**永不改写原图**（只改掩膜），且不影响未选中区域的显示。

## 4. ROI 命名与导出映射

### 4.1 命名规则（定死，不静默兜底）

- 唯一、非空、`^[\w\u4e00-\u9fa5-]{1,31}$`（Excel sheet 名上限 31 字符且禁用 `[]:*?/\`）；
- **重名时报错拒绝，不自动加后缀**——静默改名会让"导出里那张表叫什么"不可预测。

### 4.2 映射表

| 出口 | 现结构 | 多 ROI 后 |
| --- | --- | --- |
| XLSX | 单张 `pollen` sheet | 每 ROI 一张 sheet，sheet 名 = ROI 名 |
| LiPD | 硬编码 `tableName: "pollen_data"` | `paleoMeasurementTable[i].tableName = ROI 名`（LiPD 的 paleoData 本就是"一张变量表"，这是正确建模） |
| CSV / .tar | 单个 `data.csv` | `data/<roi名>.csv` 每 ROI 一份；`data.csv` 保留为主 ROI（兼容 `plot_strat.R`） |
| 绘图脚本 | 单张图 | 每 ROI 一段 `strat.plot` |

**待定**：见 §9。已定：**分块输出，列名不加 ROI 前缀**
（每 ROI 一份 `data/<roi名>.csv`；XLSX 每 ROI 一张 sheet；LiPD 每 ROI 一张表）。
加前缀会破坏下游 R/rioja 的列名约定，故不作为默认。

## 5. 双栏分工（用户要求一并规划）

规则：**左栏 = 多对象清单（挑选/排序/批量/概览）　右栏 = 单对象明细（精确输入/校验/本步主操作）**

### 5.1 左栏（Sidebar）：当前步骤的对象清单

现状：左栏**完全不感知步骤**，永远是属种列表，第 1–5 步全空。

### 5.3 X 轴标定：**点两个真实刻度线 + 填两个读数**（与 Y 轴同构）

**上一版设计是错的**：它把 X 标定建模成"起点值 / 满刻度值 + `startX` / `tickEndX` 两个结构位置"。
但 `startX`（列基线）**不等于**图上"0"刻度线的位置，`tickEndX` 更是我们**猜的**位置。
用户的习惯（也是正确做法）是**标记两个真实刻度端点**。

正确模型：

> 在图上点**两条真实存在的刻度线像素** → 填这两条刻度线的**读数** →
> 线性映射 `v(x) = v₁ + (x − x₁)/(x₂ − x₁)·(v₂ − v₁)`。

- 两个端点**不要求**是"列的 0 与满刻度"，可以是图上任意两条有数字的刻度线（例如 `10` 与 `50`），
  这比强行要求端点更能贴合真实图（很多列的 0 刻度线画在轴线外）；
- 列基线 `startX` 只用于 area 形状的**填充起点**，其值由映射求值得出，**不单独让用户填**；
- 默认取 **ROI 级**（见 §0.1：同组列共享标度，标一组一次），个别列走 override。

**两个端点必须显性可见**（用户批评：现在各列标记点不可见，无法判断标对没有）：

| 层级 | 显示 |
| --- | --- |
| active 列 | 两个刻度钉全显 + `0–40` / `0–30000` 数值标签 + 连接它们的微型数轴 |
| 同 ROI 其它列 | **迷你刻度齿**（2px 短线，屏幕恒定尺寸），一眼看出每列标定位置 |
| 其它 ROI | 不显示（避免糊成一片） |
| **「标定总览」开关** | 一键全显所有列的 0 齿与满刻度齿 |

### 5.3.1 刻度端点怎么来：**几何检测 + 用户肉眼读数**（**不引入 OCR**）

#### 原则：能用眼睛的，不要用 OCR 猜

> **凡是"用户本来就在看着图"的信息，优先用眼睛读。** 判据是**信息量**：
> 要读的是 **1–2 个数字** → 用眼睛；要读的是 **几十个字符串** → 用 OCR。

| 信息 | 量级 | 手段 | 理由 |
| --- | --- | --- | --- |
| 属种名标签 | **28 个拉丁名** | **OCR** | 逐个手打要几分钟；OCR 已能读（45° 矫正后） |
| 刻度读数 | **每 ROI 2 个数字** | **眼睛** | 几何路径已把成本压到两个数字；为省这两下键盘引入新旋转模式（90°）、新区域配置、新失败面与用户根本不会看的交叉校验，**投入产出不成比例** |

另：拿 OCR 去读一个**规则序列**（10,20,30,…）本身即用最不可靠的手段取最可推导的信息。
**故本设计不引入刻度数字 OCR**，也不为其保留接口。

#### 两条路径

| 路径 | 前提 | 用户成本 |
| --- | --- | --- |
| **① 几何（首选）** | 刻度线清晰等距 | **每 ROI 填 2 个数字：起始读数、步长**（自己看图读出） |
| **② 手点两刻度端点 + 填两读数** | 任何情况 | 每列 2 点击 + 2 数字（**万能兜底**） |

**① 的推导**（**不假设"列基线 = 0"**，避免引入未验证的假设）：

```
px_per_interval = (x_lastTick − x_firstTick) / (n_ticks − 1)
x₁ = x_firstTick,  v₁ = 起始读数
x₂ = x_lastTick,   v₂ = 起始读数 + (n_ticks − 1) × 步长
```

实测 `type2_exaggeration_bell.png`（起始 10 / 步长 10）：列 4（2 刻度）→ 20；列 15（4 刻度）→ 40；
列 7（7 刻度）→ 70。**28 列只需填 2 个数字。**

**为何优于纯手点**：手点要求**逐列**操作（28 列 = 56 次点击 + 56 个数字）；几何法降到**每 ROI 2 个数字**，
且错误模式更少——**点错一列会静默产生一个错标度，而区间数错会立刻表现为满刻度值异常**。

#### 校验：交给眼睛（无 OCR 后必须补上这一环）

OCR 原本承担的"交叉校验"取消后，**误读与误检**必须仍能被发现：

1. **每列派生徽章**（`0–20` / `0–40` / `0–70`）：步长读错（10 读成 100）会让整组数值明显失真，一眼可见；
2. **把检测到的刻度线画在画布上，并显示"本列检测到 N 条刻度"**——
   用户核对的是**数出来的条数**，不是数字。**条数错（刻度粘连/断开）是几何路径的主要失败模式**，
   必须让它在眼睛下暴露；
3. **检测到 0 条刻度必须明说并建议走手点路径**，**不得**给出"0 条刻度"的成功结果；
4. 配合 §5.3 的三级可见性 + 『标定总览』，28 列一眼可核。

**条带位置**：默认在 ROI 下方（或上方）自动搜索一条 x 条带；若某图的刻度画在列内部，
允许用户**手动指定条带 y 范围**——不得假设"刻度一定在 ROI 外"。

### 5.3.2 刻度检测的工作区域在 **ROI 之外**

刻度尺（scale bar）**不属于数据区**：实测该图数据区 y 267–880，刻度尺在 y 905–915，
ROI 应当把它排除。但**标定必须读到它**。因此：

> **刻度检测 / 取点的工作区域是「ROI 之外的一条 x 条带」（下方或上方），不是 ROI 内部。**

与"清理只在 ROI 内"**不冲突**——两者作用区域本就不同。**必须显式写明**，
否则会出现"清理把刻度尺当横线删掉 → 标定再也点不到"的连锁故障（另见 §5.7）。

### 5.3.3 比例提示（**不是校验**，措辞与阈值都必须按此设计）

> **正确的不变量是 `px_per_unit = (x₂ − x₁) / (v₂ − v₁)`**，只能由两个刻度端点算出。

**❌ 不可用 `满刻度值 / 列像素宽`**——实测反例（`type2_exaggeration_bell.png`）：

| 列 | 列宽 px | 刻度区间数 | `tickValue/列宽` | 真实 px/区间 |
| --- | --- | --- | --- | --- |
| 4 | 33 | 2 | 0.606 | 20.0 |
| 15 | 73 | 4 | 0.548 | 20.0 |
| 7 | 143 | 7 | 0.490 | 21.7 |

比值波动 **±24%**，因为列宽含**固定留白（约 13px）**，且**列越窄偏差越大**。
用 15% 阈值会把列 4 与列 7 这两个**正确**的列误报。

**⚠️ 即使改用 `px_per_unit`，也只是提示而非校验**：若某列刻度区间值为 5、另一列为 10，
`px_per_unit` **天然差 2 倍**，两者都对（同图里炭屑 0–100 与花粉 0–40 并用时就会这样）。
因此：

- 只把各列 `px_per_unit` **列出来**，把明显离群者**标出供复核**；
- UI 文案必须写明"**离群未必是错——不同列可以用不同刻度区间**"；
- **严禁**据此自动判错、自动纠正或阻断流程。

**首选路径是「几何检测 + 眼睛读数」**（§5.3.1）：检测刻度线 → 数区间 →
用户看图读出"起始读数 + 步长"两个数字 → 每列自动得出 `(x₁,v₁),(x₂,v₂)`。
**不引入刻度数字 OCR**（§5.3.1 原则：能读 1–2 个数字就用眼睛）。
`px_per_unit` 提示退为"几何检测不可用时"的辅助。

**同时它能反向发现分列错误**：若某列刻度端点落在列边界之外，多半是分列切错了——
这一条与刻度区间值无关，因此**是**可靠的判据。

硬约束：`startX ≤ x₁, x₂ ≤ endX`，越界**拒绝**而非夹紧。

### 5.4 标定 mark 是一等对象（补上游 G5）

上游的 mark 可**拖拽重定位**、**右键删除**，拖拽时按住 Shift 松手**不弹窗**（只挪位置不改值）。
我们采纳同样的语义，与"值在左栏填、不弹窗"并不冲突：

- **位置** ⊂ 画布（点选生成、拖拽微调、右键删除）；
- **值** ⊂ 左栏（可反复改）；
- 二者独立更新，改任何一个都立即重算换算比例。

Y 标定的两个 mark 与列刻度的两个 mark 共用这套交互。

**第三点交叉验证 Y 轴线性假设**（新增，成本极低价值高）：年代轴常用 log。
允许用户点第三个已知刻度点，若其预测值与实际读数偏差 > X%，提示"该轴可能非线性"。
两点线性标定在两端对、**中间全错**，而这个错误在图上完全看不出来。

### 5.5 命名走 OCR；**不做**批量导入名单（已定）

**列顺序 = 图上从左到右的几何顺序，不可由用户重排**（删 ▲/▼ 与 `onSwapTaxaNames`，也不做拖拽）。
理由：属种的左右位置是**图谱本身的物理属性**，让用户"重排名字"只会把名字错配到别的列。

**批量导入名单一并删除**（用户判定：有 OCR 之后它失去意义）。正确流程是：

```
分列 → 各列先给初始名 col01..colNN → OCR 识别图上标签 → 归属并按标签命名 → 用户逐列就地更正
```

### 5.5 标签归属必须按**区间**，不能按顺序（关键）

上一版设计写的"把名单按标签 x 排序后逐列赋值"**仍然是顺序配对**，一旦标签数 ≠ 列数就整体错位。改为：

> 每个 OCR 标签取其**像素 x 中心点**，落在哪个列的 `[startX, endX)` 区间就归给哪一列。

**数量不一致时不做任何配对**，而是显式对账并列出：

- **有列无标签**：哪些列没拿到名字（保持 `colxx` 初始名，标为"待命名"）；
- **有标签无列**：哪些标签的 x 没落到任何列上（通常是分列漏切或标签在 ROI 外）；
- **一对多/多对一**：同一列被多个标签命中（标签重叠），或一个标签横跨两列。

这把"标签数 vs 列数不一致"从**隐藏故障**变成**显式对账**——上游教程硬编码 `ncols = 28`
正是为了这个校验。

**OCR 整体失败时的兜底**（不得静默）：左栏列清单进入**顺序命名**模式——
逐行输入名字，输入时**画布高亮对应列**。它逐个名字对应到可见的列，因此不含任何顺序假设，
与"批量粘贴（盲配）"性质不同。

### 5.6 列名唯一性（新增，现实中必然遇到）

上游教程那张 Hoya 图自身就有 `Gramineae <40um` / `>40<50um` / `>50<60um` / `>60um`
以及重复的 `Pinus` 变体。Excel 表头与 LiPD `variableName` 都要求唯一，而当前**没有任何规则**。

规定：
- 列名在**同一 ROI 内**必须唯一；重名时报错并指出冲突的两列（**不自动加后缀**）；
- 允许的字符集与长度上限按导出目标取交集（Excel 表头无 31 字符限制，但 LiPD `variableName`
  不宜含空格与 `<>&`）→ 定一个保守白名单，越界时提示而非静默替换。

### 5.7 列内清理与标定的**参照物冲突**（新增）

刻度短线属于"对读者有信息量的干扰要素"，**正好会被第 4 步清理当作 C/D 类列内线删掉**；
而第 6 步标定又要求用户**点在刻度线上**。这是真实的顺序冲突。

规定：**标定取点一律在「原图」上进行** —— 进入标定态时自动隐藏去线叠加层与排除区遮罩，
并在右栏明示"当前显示原图，勿在此处修改清理设置"。已删除的线在标定态**仍然可见**。

### 5.8 批量改刻度真实值（改为组级后已基本不需要）

形态类型、放大倍数是**安全批量**（幂等、无歧义）。刻度真实值**不安全**。
但采用"ROI 级默认 + 单列 override"后（§0.1），批量改值**本就不需要**——
改默认即改全组。因此：只保留"改 ROI 级默认"，不提供"把若干选中列改成同一数值"的直写路径。

## 6. 第 8 步门禁重写

### 6.1 现行实现的缺陷（`PropertyPanel.ts:551`）

```ts
if (minSum >= 85 && maxSum <= 115) { /* 🟢 达标 */ }
```

- 把"偏低"也当问题报警 → **任何只画了部分属种的图必然长期亮黄灯**，报警疲劳；
- ±15% 同时**上端太松**（20 列里一列多读 20%，总和 101–115% 仍"达标"，而那是真错）**下端太错**（合规的 62% 被判异常）；
- `rowSum > 0` 才计数 → **全零层位被静默剔除**，而"这一层完全没读到数"最该报；
- 门禁在前端计算（`extractRawMatrix` + 该循环）。QA 结论是面向用户的数字，按项目不变量应由后端产出；
  这与已清除的"前端自算导出"是同一类问题。

### 6.2 新语义：方向性约束 + 三级

| 级别 | 判据 | 含义 |
| --- | --- | --- |
| 🔴 硬错误 | 任一层位 `Σ > 100% + ε` | 组成数据不可能超 100 → 一定错（放大倍数忘归一 / tickValue 设错 / 单列越界多读） |
| 🟡 单列越界 | 某列峰值 > 该列声明满刻度 | **比总和更早发现问题**：放大倍数或刻度设错的第一现场 |
| ⚪ 信息 | `Σ` 的 min/p50/max + 未覆盖比例 `100 − Σ` | 未画出/未识别属种占比；**不报警** |
| ⚪ 信息 | 空层位数与具体深度（逐条列出） | 修正现有实现的静默剔除 |

`ε` 由用户设定（默认 2%），不做隐藏魔数。

X/G/T 为初拟，需最后统一过一遍防冲突。**没有"重排序"工具**（见 §5.4）。

## 10. 验收协议（验收人：本会话）

每张任务单交付时，验收按**四层证据**逐层核，**缺一层即退回**：

### 10.1 四层证据

| 层 | 证据 | 不合格的典型 |
| --- | --- | --- |
| **L1 门禁** | `pixi run lint` / `pixi run test` / `npm --prefix frontend run build` / `npm --prefix frontend test` 全绿，并给出实际输出行 | "应该能过"；只贴命令不贴输出 |
| **L2 测试** | 新增回归测试**针对本单的行为契约**（不是覆盖率凑数），且**能在旧实现上失败** | 测试写成内联副本复刻新逻辑（本项目已有此类前科：`test-core.js` 的坐标/深度副本在真模块解耦后仍"通过"） |
| **L3 真实数据** | 在内置 Hoya 图上跑出的**具体数字**（像素行/列、计数、比例），与预期可对照 | 只报"功能正常"；用合成小图代替真实图 |
| **L4 端到端** | 起**临时端口**服务（不得占用/杀死用户 8765 的进程），浏览器实测并给出可复核的观察值 | 只截一张模糊全屏图；声称"已看过了" |

### 10.2 硬性红线（触任一条直接退回，不看其它层）

1. **编造数据**：任何面向用户的数字必须来自后端对真实输入的计算；取不到就报错并停在原地
   （`docs/ARCHITECTURE.md` §2/§9，`tests/test_no_fabrication.py`）。
2. **静默兜底**：`?? 默认值`、`isCalibrated: true` 之类把"未观测"写成"确定"。
3. **双份真相**：前端自算一套与后端并行的结果（历史上出现过：前端自算导出、前端自算去线掩膜）。
4. **破坏不变量**：平移手势（右键/中键/空格+左键三者等价）；ROI ≠ 标尺。
5. **改契约不同步文档**：RPC 方法/参数/返回字段变更未同步 `docs/ARCHITECTURE.md`
   与 `docs/JSON_RPC_SPECIFICATION.md`（新 AGENTS.md 明文要求）。
6. **碰别人的东西**：改写 `HANDOFF.md` 中他人那一节（只增改自己那节）；提交构建产物/缓存/
   他人未提交修改；破坏性 git 操作。

### 10.3 证据留痕

- 每单交付须在 PR/提交信息或交接说明里给出：**改了哪些文件**、**新增/修改了哪些测试**、
  **L3 的具体数字**、**L4 的观察值与所用端口**。
- 验收结论写回本会话；**不以"测试通过"替代"行为正确"**——L2 通过但 L3/L4 数字对不上，仍判退回。

### 10.4 验收人对"通过"的定义

> 一个任务单**通过** = 四层证据齐全 **且** L3/L4 的数字与设计稿预期一致 **且** 未触任何红线 **且**
> 我能自己复现（我重跑命令/重做浏览器步骤能得到同样结果）。

**不可复现的一律不算通过**，即使作者截图显示正确。
