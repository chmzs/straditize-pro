# 刻度齿真值（ground truth）—— task-13 权威定义

> **本文件的目的**：给 task-7（G-01a 刻度齿检测死代码修复）一个**可复跑、可证伪**的真值。
> 在它之前，46 / 49 / 31 / 110 四个数字互相矛盾，任何实现都只能靠猜。
>
> **权威脚本**：`scripts/truth/xticks_ground_truth.py`
> **一条命令**：`pixi run python scripts/truth/xticks_ground_truth.py`
>
> **本文件不接受"凑数字"**：脚本里没有任何可调 target。若结果与历史数字不同，
> 结论是**历史数字错了**，不是脚本错了。

## 0. 先回答三个必答问题

### 0.1 「46」的原始出处——**它是错的，含 16 个列框线**

| 项 | 内容 |
| :--- | :--- |
| **出处** | `scripts/prod_gate/g01_xticks_probe.py` 第 33-46 行，函数 `truth_ticks()`，字段 `n_ticks_in_330_1290` |
| **判据** | `band = a[871:876, :]`（5 行）；`dark = (band < 160).all(axis=0)`（**5 行全暗**）；合并相邻 ≤2px；再限定 `330 <= x <= 1290` |
| **可复跑** | 是，见 §0.4 |
| **问题** | 该判据**只查"5 行全暗"**，无法区分"短齿"与"贯穿整列的框线"——两者在这 5 行里都是全暗 |

实测复现（全图合并后 70 个，限 ROI 后 46 个）：

```
齿位 = [332, 357, 370, 395, 407, 432, 445, 470, 482, 507, 520, 545, 570, 582,
        607, 620, 644, 657, 682, 694, 719, 744, 769, 794, 819, 844, 869, 894,
        906, 931, 956, 981, 1006, 1031, 1056, 1081, 1094, 1118, 1131, 1156,
        1181, 1194, 1218, 1231, 1269, 1280]
```

与已测得的 16 个列边界比对，**46 个里有 16 个落在列框线位置**：

```
[332, 370, 407, 445, 482, 520, 582, 620, 657, 694, 906, 1094, 1131, 1194, 1231, 1280]
```

**结论：46 = 30 个真齿 + 16 个列框线。46 不可作真值。**

> 这是我在本轮犯的同类错误：判据（5 行全暗）没能表达它声称要表达的对象
> （"从轴线伸出的短齿"），于是把框线也算了进去。**Lead 的 49 含同样的污染**
> （他的判据是"从 870 起连续暗、876 变亮"，框线同样满足）。

### 0.2 「16 列」的口径——那是**产品分列结果**，不是齿数

| 项 | 内容 |
| :--- | :--- |
| **出处** | `scripts/prod_gate/g01_full_chain.py` 的 `[6] detect_columns` 输出 |
| **口径** | 产品的 `detect_columns` 在 ROI `[330,1330]×[233,861]` 上检出的列数 |
| **与齿的关系** | **无关**。"16/16 列"指的是"16 个检出列里每列都检到了齿"，不是说有 16 根齿 |

Lead 实测 22 列、我实测 16 列，源自 **ROI 不同**（`load_image` 自动建议的 ROI 是
`[69,1867]×[266,744]`，我手框的是 `[330,1330]×[233,861]`）。列数随 ROI 变，
本就不是稳定量，**不应作为任何真值口径**。

### 0.3 「110 个候选群」——大概率也没排除框线

backend-fixer 数出 110 个，与 46/49 的差异倍数（2.4×）说明它用了更宽的判据
（可能未排除框线、或未合并相邻列）。**本文件不猜他的判据，只给出权威定义供其对齐。**

## 1. 齿的物理定义（本真值的唯一依据）

### 1.1 图版几何（逐像素实测）

图版 `fig3_raw.jpeg`（2132×928）中每列有**自己独立的刻度小尺**：

```
y=869                        轴线：水平线，横跨该小尺的宽度
y=870 .. 873                 齿：从轴线**向下**伸出的短竖线
y≈883 .. 897                 印刷数字（0/5 等字形）—— 不是齿
```

像素块实证（`--dumps` 输出，轴线段 x=750..760）：

```
       x:  750 1 2 3 4 5 6 7 8 9 760
  y=866:  ...........            <- 数据区
  y=867:  ...........
  y=868:  ...........
  y=869:  ###########            <- 轴线（整段暗）
  y=870:  .......#...            <- 齿（从轴线向下）
  y=871:  .......#...
  y=872:  .......#...
  y=873:  .......#...
  y=874:  ...........            <- 齿结束
```

小尺样例（轴线段 x=332..358，宽 27px）：

```
       x:  332..358
  y=867:  ##.........................
  y=868:  ##.........................
  y=869:  ###########################   <- 轴线
  y=870:  ##...........#...........##   <- 齿 @ x≈345 与 x≈357
  y=871:  ##...........#...........#.
  y=872:  ##...........#...........#.
  y=873:  ##...........#...........#.
  y=874:  ##.......................#.
  y=875:  ##.......................#.
```

注意两端 `x=332/333` 与 `x=357/358` 在 **y=867/868 就是暗的**——那是**框线**
（贯穿到数据区），不是齿。这正是必须排除的对象。

### 1.2 三条判定条件（全部来自"刻度尺"这个对象的定义）

| 条件 | 内容 | 排除什么 |
| :--- | :--- | :--- |
| **T1 垂直性** | 齿是竖直细线，落在一列像素上 | 印刷数字的横向笔画 |
| **T2 从轴线伸出** | 轴线下方连续暗 **且 轴线上方 3px 内不暗** | **列框线**（贯穿全高）、图例文字 |
| **T3 在所属小尺内** | 必须落在同一条轴线段上 | 跨列误配 |

**T2 是排除框线的关键**，也正是「46 / 49 都错」的根因：那两个判据只有 T1/T2 的前半段。

### 1.3 为什么不需要"等间距"条件

图版各列小尺的刻度间隔不同（实测 gap 取值含 12/13/18/19/24/25/26/31/32/33/47/79/307），
因为不同列的量程不同。**把"等间距"当必要条件会误杀合法齿**。
间距只作为**事后合理性检查**（中位 13.0px ≈ 图版说明的小齿 12.5px），不作为判定条件。

## 2. 两种独立方法（交叉核验，不一致就报告分歧）

| 方法 | 判据 | 实现 |
| :--- | :--- | :--- |
| **M1 游程法** | 逐列从轴线下方数**连续暗长度**，落在 `[3, 8]` px 视为齿；再要求轴线上方 3px 不暗 | `teeth_by_run_length()` |
| **M2 投影法** | 取轴线下 **4 行**做列投影，**≥3 行暗**视为齿；同样要求轴线上方不暗 | `teeth_by_projection()` |

两者用**不同的中间表示**（单列游程 vs 多行列投影），且都不含可调 target。
容差 ±1px（同一根齿的抗锯齿主瓣可能被取到相邻列，属离散化误差，不是分歧）。

`pixi run python scripts/truth/xticks_ground_truth.py` 输出：

### 3.1 fig3 的齿数分布（按小尺分段，可逐段核对）

```
轴线段数 = 19
各段齿数 = [10, 2, 2, 2, 2, 2, 4, 2, 2, 2, 16, 14, 2, 4, 2, 2, 2, 6, 11]
合计      = 89
间距中位  = 13.0 px   （≈ 图版说明的小齿 12.5px）
间距取值  = [12, 13, 18, 19, 24, 25, 26, 31, 32, 33, 47, 79, 307]
```

**这个分布本身可作为合理性证据**：
- 窄小尺（宽 26px）各有 **2** 个齿 —— 与"每列只印 1–2 个刻度数字"一致；
- 宽小尺（1476..1570 等）有 **16 / 14 / 11 / 10** 个齿 —— 与"量程大的列刻度更密"一致；
- 间距中位 **13.0 ≈ 12.5**（图版说明的小齿间距），偏差来自该图的 13px 栅格。

### 3.2 hoya / beginner 为什么是 0（含 Lead 提醒的陷阱）

Lead 指出 hoya `y=1305-1325` 是图例文字（能看出 "A/C"），"轴线下方有短竖线"会误判。
**实测该陷阱被 T2 正确排除**：

- hoya 的整行级轴线候选有 14 条（`[214, 215, 507, 508, 818, 819, 1129, 1130, 1306, 1307, 1312, 1313, 1374, 1375]`），
  取最后一条 `y=1375` 作为轴线基准；
- 该行只有 **1** 个轴线段（宽 2046px），段内 M1/M2 均为 **0** 齿。

> 注意：hoya 的轴线候选里包含 `1306/1307` 与 `1312/1313`——正是 Lead 说的图例文字区。
> 若判据只取"任一轴线候选下方的短竖线"，就会在那里误判；本脚本取**最后一条**
> 整行级轴线（刻度尺应在数据区底缘），并叠加 T2，故不误判。

## 5. 给 task-7 的验收含义（重要）

### 5.1 实现正确的判据是"检出真齿"，不是"凑到 89"

| 验收项 | 要求 |
| :--- | :--- |
| fig3_raw | 检出的齿位集合与真值 **89 个齿位**在 ±2px 内匹配率 ≥ 95% |
| hoya | **0** 齿 |
| beginner | **0** 齿 |

**不要以"总数=89"为唯一判据**：那样可以通过"多检 5 个、少检 5 个"凑出来。
必须比**齿位集合**，而不是比总数。

### 5.2 三种已知的错误方向（都有历史实例）

| 错误方向 | 表现 | 后果 |
| :--- | :--- | :--- |
| 选中印刷数字带 | band 落在 y≈886-892 | 检出的是数字笔画（Lead 已实测到 backend-fixer 选中 `[886,892]`） |
| 含列框线 | 齿数虚高（46/49 即此） | 用户给框线"标定"，量程全错 |
| 凑总数 | 总数=89 但齿位错配 | 通过验收但数据不可用 |

### 5.3 一句话给 backend-fixer

**band 必须落在轴线 `y=869` 下方的 `y=870..875`，且必须用"轴线上方不暗"排除框线。**
数字区在 `y≈883+`，框线在两端贯穿——两者都不是齿。

第四次之所以可信，不是因为数字看起来对，而是因为：
① 定义先从物理对象（轴线/齿/数字三层结构）得出，不是从期望数字反推；
② 两种**不同中间表示**的方法独立得出同一结果；
③ 脚本里没有任何可调 target；
④ 有 `--dumps` 可人工目视核对。

这三条也是本文件能被当作真值的唯一理由。
