## 3. 数据质量

### 3.1 可作门禁的判据（与阈值无关）
**提取点全部落在本列 `[start,end]` 内：10192/10192 = 100.00%。**
含义：产品不会把邻列的墨迹读进本列，跨列串扰为零。这是结构性判据，可作门禁。

### 3.2 只能记 UNCERTAIN 的判据（对阈值敏感）
逐行位置偏差 |Δx|（产品取的 x vs 独立像素取的 x，同一行同一量）：

| 墨迹判据 | 比对行 | 中位 | p95 | >3px 行 |
|---|---|---|---|---|
| 灰度<128 | 3141 | 1.00px | 1.00px | 42 |
| 颜色偏离>40 | 2538 | 4.00px | 35.15px | 1476 |
| 颜色偏离>60 | 1445 | 1.00px | 49.00px | 137 |
| 颜色偏离>80 | 2488 | 0.00px | 6.00px | 137 |

**这个量随阈值跳动（中位 0~4px、p95 1~49px），按项目铁律不得作门禁。**
诚实结论：**产品提取的数值精度，我目前无法用自动化判据给出可信数字。**
能说的是中位偏差在 0~4px 量级（列宽 38px 的 0~10%），但尾部有 1~5% 的行偏差较大，
其成因已定位（见 §3.3），不是产品读错。

### 3.3 关于 Lead 的 `70.59% vs 71.05%，偏差 -0.46 个百分点`
**该数字不可复现，不得作为数据质量证据。** 依据：
- 仓库内全量 grep `70.59` / `71.05` 零命中（除依赖包无关匹配），无任何脚本或文档产出过这两个数。
- Lead 记录的标定 `x_ticks=[{px:339,value:0},{px:477,value:100}]` 在产品里**直接被拒**：
  ```
  参数范围越界：刻度点像素 (339.0, 477.0) 超出该列物理范围 [322.0, 380.0]
  ```
  说明 Lead 当时的列划分与记录下的刻度像素不属于同一列——两者不可能同时成立。
- 在 cleanup×reader_type 六种组合下扫描，70.59 一次都没出现。
- 未标定时产品走 legacy 映射 `[start,tickEndX]→[0,20]`，全表 max=43.25；
  用"行内墨迹宽度占列宽"口径全表 max=98.04。两个都不是 70.59。

我**不调参去凑 70.59**。记为 UNCERTAIN，并把可复现的结构判据（§3.1）作为替代证据。

## 4. 四次误判复盘 + 我自己重犯的同型错误

### 4.1 Lead 的四次

| 次数 | 判据声称测什么 | 实际测了什么 | 正确读法 |
|---|---|---|---|
| 1 | `r.get('labels')` 判 OCR 结果 | 顶层无 `labels` 键 → 恒 None → 判"OCR 失效" | 标签在 `r['data']['labels']`，先 `print(list(r.keys()))` |
| 2 | `lb.get('text')` / `lb.get('name')` | 字段名不存在 → 恒 None → 判"16 个空标签" | 真字段名 `ocr_text` / `suggested_name` / `suggested_zh` |

| 4 | 仍未先读返回结构 | 同一错误延续 | 取值前先打印键名 |

## 5. 下次验证 OCR / 提取前必做的三件事

固化进脚本（`verify_pdf_to_data.py` 已全部落实）：

1. **先 `print(list(result.keys()))` 看返回结构，再取值。**
   嵌套的也要看：`list(r['data'].keys())`、`list(labels[0].keys())`。
   脚本里每个后端返回都先 `show_keys()` 再取字段。

2. **读到的字段若全为 None，先怀疑字段名错，不要先怀疑产品坏。**
   判据：若"全部为 None"而不是"部分为 None"，几乎必然是字段名或层级错。
   脚本把这条做成硬提示：`associated_column_id` 全 None 时，先跑内置对照实验
   证明原因，再下结论。

3. **用产品口径构造真值，不要用直觉口径。**
   本例：产品算"行内墨迹宽度占比"，直觉口径"墨迹行占比"差 36 个百分点。
   脚本用 `resolve_column_scale` 读出的真实映射参数构造真值，不猜。

补充两条（本轮新增，同样写进脚本）：

4. **判据不得对参数敏感。** 实测同一目标在 4 套阈值下给出中位 0~4px、p95 1~49px。
   敏感就标 UNCERTAIN，不许当门禁。
5. **模拟用户真实路径，不要直调 API 就下结论。** 前端可能有兜底逻辑，
   后端直调失败 ≠ 用户走不通。

## 6. 仍需用户手工的环节（按能否自动化排序）

### 6.1 可以自动化，只是还没做（优先级高）
1. **建议 ROI 的底部边界**。当前建议框漏掉底部 125px。
   后端 `suggest_data_region()` 用历史比例启发式，没利用"横轴线"这一强结构特征。
   可行做法：检测横贯全宽的暗行（本次实测横轴暗像素占全宽 **66.1%**，脚本输出原文
   `横轴线行 y=869 (暗像素占全宽 66.1%)`），
   以它为数据区底边。这项**完全可自动化**，且是用户第一屏就会踩的坑。
2. **OCR 标签与列的关联**。当前被 `len(labels)!=len(columns)` 硬门整体拒绝。
   内置对照实验证明：删掉 1 个重复锚点标签使 17→16 后，**16/16 列全部关联成功**。
   可行做法：保留"计数不等时不做 1:1 配对"的原意，但**至少输出位置归属**
   （哪个标签落在哪个列），而不是全部置 None 且无提示。

   **根因已定位到具体一行（追加，见 `scripts/product_journey/probe_ocr_pairing.py`）**：
   ```
   straditize_core/session_parts/ocr.py:40
       y0 = max(0, int(self.data_ylim[0] - 320))
   本例 data_ylim[0] = 233  ->  233 - 320 = -87  ->  max(0, -87) = 0
   ```
   `max(0,·)` 把负值夹成 0，标签带从**图像最顶端**开始，于是把标签区上方的
   图例文字 `Herbs`（anchor_y=57.9，比标签行低处 221.2 高出 163.3px）也扫进来，
   多出第 17 个假标签 → 触发计数硬门 → 16 个真标签的关联被整体否决。

   实测 y0 扫描（唯一变量 y0，x0/x1/y1 固定）：
   ```
   bbox=[330,  0,1330,230]  -> 17 标签  matched=False  assigned=0   （含 Herbs）
   bbox=[330, 20,1330,230]  -> 16 标签  matched=True   assigned=16  （图例已排除）
   bbox=[330,150,1330,230]  -> 16 标签  matched=True   assigned=16
   ```
   最小可用 y0=20，由扫描实测得出（非预设）。

   ⚠️ 一条已证伪的旧假说，留档以免重犯：**"旋转标签 bbox 超列宽
   （66-89px vs 37px）导致失败"不成立**。实测 bbox 横向跨度为
   min 62.2 / 中位 118.8 / max 170.4（66.4 是 Abies、89.1 是 Picea，最窄的两个），
   且把 bbox 压成一个点（跨度 0）后 `matched` 仍为 False、`assigned` 仍为 0
   ——若宽度是原因，压点必须变绿。证伪实验见 `probe_ocr_pairing.py` 第 ③ 组。

3. **`unrecognized` 标签的采纳**。5 个标签因置信度 0.50 被判 unrecognized，
   UI 默认不勾选，用户需手动勾。属种名文本其实是对的（Quercus (D)/(E)、
   Euphorbiaceae、Conc、Herbs），只是词典没匹配上中文名。

### 6.2 必须用户手工，无法自动化（合理）
4. **属种名的最终核对**。OCR 给出 `Caryophyllacea`（少 e）、`<Myriophyll`（截断）、
   `Conc`/`Herbs`（图例缩写）。这些需要研究者按专业知识判断，不该自动改写——
   自动"纠正"一个属种名属于伪造数据。
5. **X 轴刻度读数标定**。图上刻度数字的物理含义（% 还是粒/克）只有作者知道。
   产品提供"拾取两个端点 + 填读数"，这是正确的设计，不该自动化。
6. **数据区边界确认**。即便建议 ROI 改准了，最终仍需用户看一眼确认——
   图版常有图例、注释、多面板混排，机器判断不能替代。

## 7. 距离"好产品"还差什么（最重要的部分，直说）

按对用户的伤害程度排序：

1. **"静默"是这个产品当前最大的敌人。** 三处 PARTIAL 有一个共同形态：
   产品做了决定，但不告诉用户。建议 ROI 少框 125px 不说、17 个标签关联全失败不说、
   5 个标签需要手动勾选也不说。用户不会看到任何异常，只会拿到一份少了数据的 CSV。
   这比报错危险得多——报错会被发现，静默不会。

2. **数据精度当前无法自证。** 我能证明"提取点不越界"（100%），但无法给出
   "提取值有多准"的可信数字——因为我没有一张有权威真值的标准图版。
   **这是交付前最该补的基础设施**：需要一张人工逐行标注过曲线 x 位置的图，
   作为回归基准。没有它，任何"精度提升"都无法验证是提升还是漂移。

3. **OCR 的关联硬门是"正确但无用"的设计。** 防错配的意图是对的，
   但代价是 17 个正确识别的标签一个都用不上。正确做法是分级：
   位置明确归属的照常给出，只在真正歧义处（多标签同列/跨列）才拒绝。

4. **列宽 37px 与刻度间距 25px 的物理矛盾尚未解决。** 每列最多 1 个齿，
   而标定需要 2 个点。这意味着**自动标定在这类高密度花粉图上原理上做不到**，
   必须用户手工。产品目前没把这件事说清楚，`usable 4/16` 这个数字用户看不到。

5. **可复现的验收脚本现在是有了，但它只覆盖一条链路。** 本次覆盖

## 追加：OCR 关联失败的真正根因（Lead 隔离实验，2026-10-23 修正）

> 本节纠正本文档与提交 `6613edd` 中关于 OCR 关联失败根因的错误表述。

### 之前两版说法都不成立

| 版本 | 说法 | 为何错 |
|---|---|---|
| 第一版（Lead） | 「17 标签全部关联」 | 实际 `associated_column_id` 0/17 全 None |
| 第二版（`6613edd`） | 「bbox 超列宽（66-89px vs 37px）导致失败」 | bbox 压成一个点后仍失败，机制不成立 |

### 决定性隔离实验（只改一个变量）

```
bbox=[330, 0,   1330, 238]  angle=45  →  labels=17  matched=False  assigned=0
bbox=[330, 80,  1330, 230]  angle=45  →  labels=16  matched=True   assigned=16
bbox=[330, 80,  1330, 230]  angle=90  →  labels=3   matched=False  assigned=0
bbox=[330, 80,  1330, 230]  angle=0   →  labels=6   matched=False  assigned=0
```
同一图像、同一引擎、同一列集，**唯一变量是 bbox 的 y0**：
- `y0=0` → 17 个标签（多一个 `Herbs` 假标签），`can_pair` 因计数 17≠16 整体放弃
- `y0=80` → 16 个标签，16/16 全部正确关联

### 真正根因：默认 bbox 计算过宽

`straditize_core/session_parts/ocr.py:40`：
```python
y0 = max(0, int(self.data_ylim[0] - 320))
```
本例 `data_ylim[0] = 233`，`233 - 320 = -87` → `y0 = max(0, -87) = 0`。
即默认 bbox **从图像最顶端开始**，把标签区上方的图例文字（`Herbs`）也纳入识别范围，多出一个标签，进而触发 `can_pair` 的计数硬门整体否决。

### 两个连带事实

1. **OCR 是确定性的**：同一输入连续调用 5 次，全部 `labels=16 matched=True assigned=16`。不存在随机性。
2. **`ambiguous` 不是 `can_pair` 的输入**：它是诊断输出。隔离实验中 ambiguous 从 15 变到 2 时 `matched` 仍为 False，证明二者无因果关系。

### 正确修法方向（两层，缺一不可）

1. **收紧默认 bbox**：不要用 `data_ylim[0] - 320` 这种固定大跨度。应基于图像内容定位标签行（例如从数据区上边界向上找第一条密集文字带），或至少限制跨度上限并排除图例区。
2. **拆分「位置归属」与「1:1 配对」**：即使计数不等，也应给出每个标签的位置归属（落在哪一列），只在真正歧义（同列多标签 / 跨列）处标记需人工确认。当前"计数不等就整体静默放弃"的设计，会让 17 个正确识别结果一个都用不上。

### 教训

这是本轮第 6 次「判据没指向对象」：前五次是读错字段名/口径，这次是**把"相关"当成了"因果"**——`ambiguous=15` 与 `matched=False` 同时出现，就断定前者导致后者，而隔离实验证明二者无因果关系。**同时出现的两件事，不等于一件导致另一件。**

## 追加：两处归因被正交隔离实验证伪（Lead 复核确认）

> 本节纠正本文档与 `6613edd` / `be9eaec` 中两处归因错误。缺陷本身是真的，但**因果链写错了**。

### 纠正 1：「列数 22 vs 16 由底部漏 125px 造成」——不成立

正交隔离（同一图、同参数，只改一个维度）：
```
建议X + 建议Y  [69,1867]×[266,744]  → 23 列
手框X + 手框Y  [330,1330]×[233,869] → 16 列
建议X + 手框Y  [69,1867]×[233,869]  → 22 列   ← 换 Y 不变
手框X + 建议Y  [330,1330]×[266,744] → 16 列   ← 换 Y 不变
固定手框 X，Y 取 [266,744] / [233,869] / [744,869] → 三者都是 16 列
```
**结论：列数差 100% 由 X 范围决定**（建议框 69..1867 把轴外文字/框线也切进列），**与 ylim 底部无关**。

但**数据丢失本身是真的**，由另一条证据支撑（不依赖列数）：
- `digitize` 用 ROI 的 `y0/y1` 当读取行区间（`digitize.py:65-70`）
- 实跑逐列 digitize：建议框读到行范围 min=266 / max=744；手框 min=233 / max=869
- **仅手框可达的行 = 108 行**（744→869 区间）

即：底部层位真的读不到，但"列数从 16 变 22"不是它造成的。

### 纠正 2：「OCR 后 16 列全叫 col01..col16」——不成立

真实 UI 链路（建议 ROI → 23 列 → OCR → 前端表格）：
```
后端：22 标签 / 23 列，matched=False，ambiguous=20
前端 OcrReviewTable.ts:57-60 按 anchor_x 兜底 → 20/23 列填上真实属种名
未配上：仅 3 列（索引 0, 2, 22）
```
**后端 `matched=False` 为真，但界面层症状不是"全空"**——前端兜底接住了 20/23。我之前说"16 列全叫 col01"只在"后端返回值"这一层成立，在"用户看到什么"这一层不成立。

### 教训（本轮第 7 次同类错误）

前六次是读错字段名 / 口径混用 / 把相关当因果。这次是**没有做正交隔离就归因**：
- 看到「建议框 22 列、手框 16 列、建议框底部少 125px」三个事实同时出现，就断定"漏底部导致多列"
- 实际只要固定 X 只变 Y，就能看出列数完全不受 Y 影响

**方法教训：当一个结果可能有多个原因时，必须固定其余变量逐一验证。相关性不是因果，正交隔离才是。**

对三类图版的标签带做连通域分析，**连通域数是可自动判定的分界线**：

| 图版 | 连通域数 | 中位字宽 | OCR 实测 |
|:---|:---|:---|:---|
| Han 2026 Fig.3（45° 旋转标签） | **172** | 15px | ✅ 17 标签全对，16/16 关联 |
| Pollen 基准图（横排密集） | **5** | 3px | ❌ 仅 4 个文字区 |

**根因**：Pollen 基准图的 36 个属种名**竖排紧邻、无间隙**，DBNet 的连通域把它们

**结论**：当前 OCR 架构适用于"标签独立可辨"的图版（45° 斜排、字间有留白），

四种角度（0/45/90/270）实测均只识别 1-4 个，证明不是 `angle_deg` 设错。

**产品应该怎么做**：载入后先算标签带连通域数，低于阈值（如 < 列数 × 0.5）时
**明确告知用户"此图版属种名密集，自动识别不可用，请手工填写"**，而不是让用户
点一次 OCR 得到几个残缺结果后自己猜为什么。

## 追加：纠正「分列漏检」的误判，并定位真正的缺陷

### 我之前的判断是错的

上一节写「软件分列数（21）低于图上实际竖线数（24–29），更低于真值属种数（36），说明分列漏检边界」。**这个判断不成立**，两条理由：

**理由 1：图版本来就没有 36 条列边界线。**
riojaPlot 的默认风格不给每个属种画独立边框。用「整段全暗」判据找边框，原始候选 42 条，剔除规则条纹（每 3px 一条的网纹填充）后只剩 **17 条**，间距 13–140px、中位 60px。

**理由 2：图上可分辨的列数就是 17–18，不是 36。**
在数据区取多行看墨迹分段，稳定得到 **17–18 段**：

```
y=250  墨迹段数=17
y=300  墨迹段数=17
y=450  墨迹段数=18
```

数据区宽 937px，若真按 36 属种均分应 26px/属种；而软件平均 44.6px/列。**36 个属种在这张图上视觉已融合，无法逐列分辨**。

所以「21 vs 36」不是漏检，而是**把真值表的属种数当成了图版的可分辨列数**——这两件事不是一回事。**我拿"真值表有 36 列"当"图上应该有 36 列"，是又一次判据指向错对象。**

### 真正的缺陷：col21 把非数据区当成了数据列

逐列量化「逐行墨迹宽度的变异系数（CV）」：

| 列 | 行数 | 宽度均值 | CV | 判定 |
|:---|:---:|:---:|:---:|:---|
| col1  x=[112,213] | 369 | 43.6px | **0.768** | 真实曲线（宽度随行变化） |
| col15 x=[717,812] | 193 | 36.3px | **0.860** | 真实曲线 |
| **col21 x=[929,1055]** | 369 | **123.4px** | **0.008** | ❌ **非曲线** |

col21 的逐行墨迹宽度几乎恒定（std=1.0px），是一整块矩形填充，被当成数据列纳入。

同一图右侧 `x=929..968` 还有 13 条每 3px 一条的规则条纹——那是网纹/阴影填充纹理，不是列边界。

### 判据说明（可复用）

**「逐行墨迹宽度的变异系数」能干净区分曲线与色块**：
- 曲线：宽度随层位变化，CV 通常 > 0.5
- 色块/文字/网纹：宽度恒定，CV < 0.1

实测三个样本：曲线 0.768 / 0.860，色块 0.008，差两个数量级。这个判据不依赖阈值调参，也不依赖真值。

### 待办（已明确，未实施）

分列后应剔除 CV 极低（如 < 0.1）的列——它们不是曲线，纳入会污染导出数据。需先确认这类列在各图版上的普遍程度，再决定是「剔除」还是「标记为可疑并提示用户」。

## 追加：纠正「三风格精度对照」的口径错误 —— 那些相关数字不能用

### 我上一节报的数字有问题

上一节给出：

| 风格 | 相关中位 | 相关>0.7 的列 |
|:---|:---:|:---:|
| area | 0.693 | 10/21 |
| bar | 0.700 | 10/21 |
| curve | 0.553 | 7/21 |

并据此判断「curve 明显最差」。**这个结论不成立**，因为「最佳匹配相关」这个口径本身有缺陷。

### 缺陷：允许任意列匹配任意真值列，天然产生重复

`bench_plot_styles.py` 的做法是：每个软件列与**全部 36 个真值列**求相关，取最大值。它**不要求一对一**，于是多列可以匹配到同一条真值曲线。实测重复情况：

| 风格 | 软件列数 | 匹配到不同真值列数 | 重复匹配 |
|:---|:---:|:---:|:---|
| area | 20 | **13** | Pinus sylvestris×3、Veronica×3、Urtica×2、Corylus-Myrica×2、Juniperus communis×2 |
| bar | 21 | **9** | Alnus glutinosa×5、Salix×5、Oxyria-type×4、Juniperus communis×2 |
| curve | 21 | **12** | Ulmus×3、Alnus glutinosa×2、Pinus sylvestris×2、Anthyllis vulneraria×2、Betula×2、Veronica×2、Saxifraga spp2×2、Juniperus communis×2 |

bar 风格 21 个软件列只对上 **9 个**不同真值列，`Alnus glutinosa` 被 5 列同时匹配——这显然不是「读数精度 0.70」，而是**列错位 + 口径允许重复**的混合产物。

### 因此

- **「curve 比 area/bar 低 0.15」不能作为「line 读数逻辑有问题」的证据。** 差异里混入了列错位与重复匹配。
- 三风格的真实读数精度**目前无法测**，因为缺「软件列 ↔ 真值属种」的一对一映射。
- 上一节「三风格精度对照」的数字**只能作参考观测值，不能作门禁**。

### 要测精度，必须先补的前提

按顺序需要：
1. **建立列-属种一对一映射**：可用 OCR 识别出的属种名（Han2026 上已能 16/16 全对），或用图版上印刷的标签位置与列 x 范围对应。riojaPlot 图上属种名是竖排紧邻的，OCR 在这类图上不可用（见上一节能力边界），所以需要别的办法——例如按真值表的属种顺序与图上列顺序做单调对齐（DTW / 匈牙利算法），并**用真值表的数值形状验证对齐是否正确**。
2. 有了映射后，才能逐列算真实偏差（MAE / 相关），也才能判断 `line` 读数是否需要改。

### 教训（本轮第 9 次同类）

**判据允许什么，就会得到什么。** 「最佳匹配」允许重复，于是得到了一组被重复匹配污染的相关值，我却把它当成精度读数在用。这与之前几次（把 ambiguous 当因果、把 bbox 越界当原因、把真值表列数当图上列数）是同一族错误：**判据的结构决定了它能不能支撑这个结论。**
