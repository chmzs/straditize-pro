## 0. 一句话

**软件对"彩色曲线"与"灰色曲线"的实心填充识别失败，15 列中有 9 列丢失 52–100% 的曲线像素。**
这不是精度问题，是提取链路里 `extract_foreground()` 恒用灰度 Otsu 造成的**功能缺陷**。

## 0.5 【D-0 严重】浅色阴影被反向处理：蓝色判实心、粉色判阴影

> 由 `qa-reviewer` 独立发现，Lead 已独立复现确认。**这是本轮最严重的缺陷**：
> 它会让读数**放大 5 倍**，且**看起来一切正常**。

### 症状（Lead 实测复现）

`build_foreground()` 对**同一种对象**（图注明写为 "5× 夸张阴影" 的浅色层）给出相反判定：

```
mode=standard           浅蓝阴影 (218,226,237) 29677px → 判前景 29373 (99.0%)
                        浅粉阴影 (244,226,226) 39143px → 判前景  3122 ( 8.0%)

mode=solid-over-shadow  浅蓝阴影 → 95.7%
                        浅粉阴影 →  0.8%
```

即 `Quercus E / Rosaceae / Chenopodiaceae`（蓝色系）的阴影层被当成实心，
读数会**系统性放大 5 倍**；而红色系列则正常。

### 为什么比 D-1 更危险

D-1（灰色填充被切掉）是"少读"，图上看得见（曲线消失），用户会发现。
D-0 是"**多读 5 倍**"，界面上完全正常 —— 数字直接进论文。
这正是 `docs/ARCHITECTURE.md` §2 最忌讳的形态：**不是没有数据，是错误的数据**
且没有任何提示。

### QA 给出的几何证明（可证伪预言）

图注写 "Shadings are five-fold exaggerated"。若浅层确是 5× 包络：

```
跨 352 个可用行，浅层跨度 / 深层跨度：
  median = 5.61   mean = 5.66   p25 = 5.42   p75 = 5.83
  落在 [4,6] 的行占 88.4%
```

**中位数 5.61 与 "five-fold" 吻合** → 浅层确实是包络，不可能是实心。
另有：31/31 行浅蓝都延伸到深蓝之外、0 行相反；深蓝锚定列轴线（中位偏移 1.0px），
浅蓝从 10–15px 才开始。

### 根因

`light_overlay_colored_mask()` 用 **饱和度 ≥ 0.08** 判彩色：

```
浅蓝阴影 (218,226,237)  sat = 0.08017  → 恰好过线  → 判"彩色"→ 进 solid
浅粉阴影 (244,226,226)  sat = 0.07400  → 不过线    → 判"灰阶"→ 按亮度走
```

两列只差 0.006，判定却相反。`tests/unit/test_metric_sanity.py` 已把这条钉住：
蓝色通道减 1（`(218,226,236)`）就能翻转分类。

**本质**：亮度阈值与饱和度阈值是两条互相打架的判据，谁也管不住谁。

### 验收判据

| 判据 | 当前 | 目标 |
| :--- | ---: | ---: |
| 浅蓝阴影进入 solid 比例 | 95.7% / 99.0% | **0%** |
| 浅粉阴影进入 solid 比例 | 0.8% / 8.0% | **0%** |
| 两种阴影是否同向处理 | 否（相反） | **是** |

**建议修法**：分层判据应改为**单一、可证伪**的量 —— 以"该像素所在列的浅层/深层跨度比"
作为依据（QA 的 `p9_p10_fivefold.py` 已给出方法），而不是亮度或饱和度的绝对值。

## 1. 缺陷 D-1【严重】提取链路恒用灰度 Otsu，彩色/灰色曲线被丢弃

### 1.1 症状（可量化）

对同一张图版，用软件默认路径 `extract_foreground()`（Otsu 阈值 = **138.0**）后，
逐列统计"实心填充像素被识别为前景的比例"：

| 属种 | 曲线颜色 | 识别率 | 判定 |
| :--- | :--- | ---: | :--- |
| Quercus(E) | 深蓝 `(0,62,137)` | 97.0% | ✅ |
| Hippophae | 黑 `(0,0,0)` | 100% | ✅ |
| Euphorbiaceae | 黑 | 100% | ✅ |
| Cyperaceae | 黑 | 100% | ✅ |
| Artemisia | 黑 | 100% | ✅ |
| Poaceae | 黑 | 97.2% | ✅ |
| **Chenopodiaceae** | 深蓝 | **75.3%** | ❌ |
| **Quercus D** | 深红 `(180,60,60)` | **47.8%** | ❌ |
| **Rosaceae** | 深蓝 | **35.4%** | ❌ |
| **Betula** | 深红 | **32.0%** | ❌ |
| **Picea** | 深红 | **13.1%** | ❌ |
| **Ranunculaceae** | 黑（但细） | **10.4%** | ❌ |
| **Pinus** | 深红 | **9.5%** | ❌ |
| **Abies** | 深红 | **8.6%** | ❌ |
| **Caryophyllaceae** | 中灰 `(182,182,182)` | **0.1%** | ❌ |

**9/15 列失败**，合计丢失 **14,804** 个实心像素（占失败列实心总量的 62%）。

### 1.2 根因（file:line）

`straditize_core/image.py` **已经实现了**多种提取模式，包括
`light-overlay-white`、`light-ink-dark`、`guided`（`build_foreground()`，`image.py:643-690`）：

```python
if ext_mode in ['standard', 'dark-ink-light']:
    auto_foreground = alpha & (rgb.sum(axis=-1) <= threshold)      # ← 只认深色
elif ext_mode == 'light-ink-dark':
    ...
elif ext_mode == 'light-overlay-white':
    bright = rgb.sum(axis=-1) > threshold
    colored = light_overlay_colored_mask(rgb)
    auto_foreground = alpha & (~bright | colored)                  # ← 能认彩色
```

**但这条能力从未被接到产品路径上**：

- `straditize_core/session_parts/core.py:470` `extract_foreground(threshold=None, mode="otsu")`
  —— 内部先 `self.image.convert("L")` 转灰度，再算 Otsu（实测 **138.0**）；
- 三处调用点全部**无参调用**：
  - `core.py:617`（`suggest_data_region` 前）
  - `core.py:1114`（线检测前）
  - `session_parts/digitize.py:84`（**数字化主路径**）
- `grep extraction_mode straditize_core/rpc_methods/*.py frontend/src/types/*.ts` → **零命中**：
  RPC 与前端从未暴露该参数。

即：`image.py` 里那套彩色/浅色能力是**死代码**，产品永远走 `standard` 灰度分支。

### 1.3 为什么彩色列也部分被识别

深红 `(180,60,60)` 的灰度 ≈ `127`，低于 Otsu 138 → 边缘/深的部分能过；
但浅红 `(244,226,226)` 灰度 ≈ `228` → 全丢。于是**同一列只有"最深处"被读到**，
曲线被人为削细 —— 这会让读数系统性偏小，且偏小多少取决于配色，**不可预测**。

### 1.4 附带发现：`light-overlay-white` 本身也不可靠

即使手动切到该模式，`light_overlay_colored_mask()`（`image.py:622-630`）用
**饱和度 ≥ 0.08** 判彩色，恰好卡在本图的阴影线上：

```
浅粉阴影 (244,226,226)  sat = 0.074  → 不过阈值（被丢弃）
浅蓝阴影 (218,226,237)  sat = 0.080  → 刚好过阈值（被当前景！）
```

实测切到该模式后（同一张图、同一批列）：

| 属种 | standard | light-overlay-white |
| :--- | ---: | ---: |
| Pinus（深红） | 9.5% | **55.9%** |
| Abies（深红） | 8.6% | **48.2%** |
| Picea（深红） | 13.1% | **80.4%** |
| Betula（深红） | 32.0% | 92.6% |
| Caryophyllaceae（中灰） | 0.1% | **27.7%** |
| Ranunculaceae | 10.4% | 89.0% |
| 其余 8 列 | 75–100% | 100% |

**结论**：`light-overlay-white` 显著改善但仍不达标（Pinus 55.9%、Caryophyllaceae 27.7%）。
**更精确的表述（经 QA 复核修正）**：就**阴影分层**而言，真形态不是"两个模式各错一半"，
而是「**两种阴影各错一半**」——浅粉 (244,226,226) sat=0.074 被判为灰阶（按亮度走，正确排除），
浅蓝 (218,226,237) sat=0.08017 越过 0.08 阈值被判为彩色（纳入前景，×5 放大）。
同一个函数对同一种对象给出相反判定，见 §0.5（D-0）。

**需要的是一种新模式**：按颜色簇把「实心层」与「阴影层」分离成两个独立掩膜，
分别导出，而不是二选一。本报告 §1.5 的验收判据就是按此写的。

### 1.5 验收判据（修好后应满足）

用本图版跑，应同时满足：
1. 15 列实心识别率**全部 ≥ 95%**；
2. 浅色阴影像素被判前景的比例 **= 0**（当前 0，不能退化）；
3. `extraction_mode` 能从 RPC 传进来，且 UI 可切换；
4. 深浅两层能**分别导出**（真实值层 / 夸张层），而不是只取其一。

## 2. 缺陷 D-2【中】刻度尺读数无法从图版自动获取

### 2.1 观察

图版每列底部有独立刻度尺：

- 刻线间距**统一 12.3 px/格**（15 列全部一致，已逐列实测）
- 宽列印了数字：`Euphorbiaceae 20/40/60/80`、`Cyperaceae 20/40/60`
- **窄列（10 列）只有 3 格且不印数字**

### 2.2 为什么这是软件问题而非用户问题

Step 6 的标定界面要求用户**手工输入两个读数**。对 15 列 × 每列 2 个数字 = 30 次人工判读，
且 10 列根本没有数字可读。

正确的做法应该是：既然刻线是**等距线性**且**列宽 = 格数 × 12.3px**，
软件可以：

1. 自动检出每列刻线与格数（本实验已证明可行：`12.3px/格` 精确一致）；
2. 让用户**只输入一列**的满量程，其余列按格数比例自动填充**建议值**；
3. 建议值必须**显式标注为"建议"**，不得直接落库（见 `agent-mcp-design.md` 的 provenance 设计）。

当前实现把"读数是人工判读量"这条正确原则，实现成了"每列都要人工重复劳动"，
反而促使用户去猜 —— 而猜就是编造。

### 2.3 验收判据

- Step 6 能显示"本 ROI 共 N 列，刻线间距 X px，格数 [3,3,3,…,18]"；
- 提供"应用同组标定"（已有 `btn-apply-ticks-to-group`）但**按格数比例缩放**，
  而不是复制同一组绝对数字；
- 落库前弹确认，或标注 `provenance.source = "suggested_from_ticks"`。

## 3. 缺陷 D-3【中】"5× 夸张层"这类图注信息没有承载位置

### 3.1 观察

Fig. 3 图注明写 **"Shadings are five-fold exaggerated"**。这是**读数的元信息**：
不知道它，就会把阴影当数据、把数值放大 5 倍（本实验中我确实先踩了这个坑）。

软件里没有任何字段承载"本图存在夸张层 / 放大倍数是多少"。`exaggeration_mult`
字段存在，但语义是"列级放大倍数用于换算"，不是"图版存在一层仅供目视的夸张包络"。

### 3.2 建议

在 ROI 或列级增加 `visual_overlay` 元信息（是否含夸张层、倍数、颜色），
并让导出明确记录"本列读数取自实心层，阴影层为 5× 视效，未参与计算"。
