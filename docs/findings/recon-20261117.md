## 2. S1 小列识别偏位：0 点比墨迹静止位左移 4px

### 复现

```python
s = load()                              # 见 §1
s._extract_foreground_from_settings()
measure_axis_stroke(gray, [939, 999, ...])
#   → 17 列返回 1、Quercus 返回 2、Artemisia 返回 0（填充型列的"无轴"告警）
#   （实测落在 ROI 子图上；全图坐标下该函数对 19 列全部返回 0，见列几何备注）
resolve_column_scale(s, s.columns[0]).abs_px0          # → 940.0  (= startX 939 + 组轴粗 1)
min(p["x"] for p in payload["columns"][0]["points"])   # → 944.0  = 曲线静止位 = startX+5
# 注：用 `core.digitize` 现算时 min 会给出 939 —— 那是取样窗口首/末行"本行无墨迹"时
# 回落 c_start 的既有行为（见 tests/unit/test_solid_block_frame_line.py 的同类说明），
# 不是曲线位置。故本报告一律用**归档控制点**的最小 x 作为"静止位"。
```

### 数据证据

1. **轴线墨迹实际跨度 5px**（Picea 列，`y=330..470` 全行中位灰度）：

   | x | 939 | 940 | 941 | 942 | 943 | 944 | 945 |
   |:--|:--|:--|:--|:--|:--|:--|:--|
   | 中位灰度 | 165 | 36 | 4 | 1 | 19 | 133 | 237 |

   即：939 与 944 是抗锯齿过渡列，940–943 是实心轴芯。曲线/填充的**静止位**（该列
   无墨迹时的最右墨迹）在 x=944 —— 由 19 列的归档控制点直接量出，16/19 列落在
   `startX+5`（col07 与 Typha 为 +2、Brassicaceae +4，对应它们更细的轴线）。

2. **0 点被定义成 `start + 1`**：`xscale.py:544` `_zero = c_start + _stroke`，
   `_stroke` 取组级 1（`core.py:1506-1520` 把 `measure_axis_stroke` 的**中位数**写进组）。
   `measure_axis_stroke`（`columns.py:374`）把"首列"当轴芯种子：首列 x=939 的均值是
   165，下一列 940 是 36，跳变 129 > `level_tol=25`，于是判定"轴线 1px 就结束了"。
   **轴线的左缘落在抗锯齿列上时，这个函数恰好把轴粗量成 1。**

3. **后果是常数偏移**：`读 = (x − 940) × 0.2381`，曲线停在轴线右缘的行 → 0.9524。
   `data.csv` 里 17 个 % 列的极小值：

   | 列 | min | 说明 |
   |:--|:--|:--|
   | Picea / Lamiaceae | 0.4762 | 2px |
   | Typha | 0.7143 | 3px |
   | Pinus, Quercus, Nitraria, Ephedra, Artemisia…（12 列） | **0.9524** | 4px |
   | col07 | 0.2381 | 1px |

   203×17 = 3451 个单元格里 **0 个真零**。一张 17 类孢粉的百分比图，在任何层位都
   没有一类缺席，这在花粉谱上不成立；而 0.9524 恰等于 4×0.2381，即偏移量本身。

4. **小列受害最重**（与用户"小列不如轮廓线"的说法同向）：grp1 的满量程 =
   `(endX−startX)×tickValue` = 60×0.2381 = 14.29。4px 偏移 = 0.9524 = 满量程的
   **6.7%**；同样的绝对偏移在 Artemisia（63.57 满量程）只占 1.5%。
   对真值为 0 的层位，相对误差无界。

### 判据（可判定、可反向）①

> 对任一列，把 `resolve_column_scale(...)` 的 `abs_px0` 与该列**曲线静止位**
> （该列所有控制点里最小的 x，或用二值掩膜在若干"空行"上取最右墨迹）比较：
> 当前工程 `abs_px0 = start+1`，静止位 `= start+5`，差 4px。
> 反向：把组 `axis_stroke_px` 手改成 5，重导 `data.csv`，17 个 % 列的极小值应从
> 0.9524 变成 0.0000，且中位数整体下降 0.95。

### 修法与取舍

- **不能**简单把 `measure_axis_stroke` 的种子改到"±2px 内最暗列"就收工：它会把
  `start` 不在轴上的图（ROI 左缘带留白）一起改判，`ARCHITECTURE §19/20` 的
  `detect_columns` 右缘锚定与 hoya / beginner 基线都会动。**先出测量证据，再动手**。
- 立即可做且零风险的一步：**把"实测轴粗"与"生效轴粗"不一致报出来**（S1 的 PR 走这条）：
  当 `measure_axis_stroke` 的返回与组/列生效值差 ≥ 2px 时，在 `resolve_column_scale`
  的返回值上带 `stroke_suspect_px` 与等价丰度偏差，导出/QA 面板照 `origin_suspect`
  的既有通道提示。用户能立刻看到"你这张图 0 点可能偏 4px ≈ 0.95%"。
- 真正的修复（改 0 点口径）必须连带：`tickEndX` 重写（当前 19 列都写成 `start+2`，
  同样偏 3px）、step-6 面板的轴粗输入、以及组斜率标定时的 0 点 —— 一次性迁移，
  属于 §6.4 的口径变更，不在本次三个 PR 的范围内。

### 影响面

`xscale.resolve_column_scale` 是全仓唯一的 X 标度入口（CSV/XLSX/LiPD/TAR/网格/QA/
画布绿线），所以这条偏移对**所有出口同时生效** —— 不存在"只有导出错、画布对"的情况。
凡是 `axis_stroke_px` 由 `measure_axis_stroke` 自动写入且该图轴线带抗锯齿的工程，
读数整体偏 1 个轴粗。

## 3. S2 横线检测只到一条；手动清除线无效

### 3.1 子症状 A：4 条真区带线只检出 1 条

**复现**

```python
s.detect_line_candidates(roi_id="roi_1")   # → 1 条（y=671, 3px, Kind A）
```

ROI 行覆盖率（`foreground` 在该行的占比）实测：

| 行 | 覆盖率 | 厚度 | 结果 |
|:--|:--|:--|:--|
| 670–672 | 0.816–0.845 | 3px | **检出** |
| 1039–1042 | 0.999–1.000 | **4px** | 拒（`width > max_width`） |
| 1296–1299 | 0.800–0.833 | **4px** | 拒 |
| 1666–1669 | 0.977–0.982 | **4px** | 拒 |

**根因**：`lines.py:26` `_AUTO_WIDTH_RATIO = 0.0015`，`resolve_width_max`
（`lines.py:68`）= `max(3, round(2096×0.0015)) = max(3, 3) = 3`；`_projection_line_rows`
（`lines.py:86`）用 `len(chunk) <= max_width` 过滤 cluster。这张图的区带线是 4px，
**差 1 像素，三条真线全被当"太厚"扔掉**。

**判据**：同一 ROI 下，`detect_line_candidates` 必须返回 y≈671 / 1040 / 1297 / 1667
四组 Kind A；且 1105 行「0.30<覆盖率≤0.75」的行里不得新增候选（防"放宽阈值换召回、
顺手把曲线当线"）。反向：把比值调回 0.0015 → 计数 4→1。

**修法与取舍**：比值是**经验标定**（注释里写明 6px/4855px），但下限 `max(3, …)` 把
小 ROI 图的容差压到 3px，恰好卡在真实扫描件的 4px 线宽上。建议改成
`max_width = max(3, round(long_side × ratio))` **+ 一个显式的"厚度直方图"证据**：
先算 `line_width_min..8` 各厚度上的候选数，若某厚度上有一簇（≥3 条）且与
`max_width` 只差 1–2px，就把 `max_width` 抬到该簇上限，并在响应里带
`width_max_used` 与 `width_histogram`。不做无限放宽 —— 那会把列内曲线纹理当线。

### 3.2 子症状 B：手动添加的清除横线对导出无效（掩膜变了，表没变）

**复现**

```python
for c in s.columns: s.digitize(c["col_index"], "area")   # 用户此时已数字化
before = export_picea(depth=10.227)      # 13.5714
s.upsert_line_geometry(roi_id="roi_1",
                       geometry={"x0":939,"y0":1664,"x1":3030,"y1":1671},
                       axis="h", selected=True)
# → stats.removed_line_pixels = 11335（掩膜确实改了）
after  = export_picea(depth=10.227)      # 13.5714  ← 一字未变
s.rois[0]["columns_stale"]            # True
```

同时验证：**重新 `digitize` 之后**，同一行 Picea 从 997 → 939（落回 0 点），
y=1675 从 966 → 947 —— 说明几何与掩膜链路本身是对的，坏在"取数缓存不失效"。

**根因**：`cleanup.py:886` 在 `_recompose` 末尾只置 `roi["columns_stale"] = True`，
而 `column_points`（导出唯一读取的逐行点集）没有失效点；`export.py:1304`
`_ensure_export_column_points` 只在 `column_points` **为空**时补点，于是导出读到的是
上一次 `core.digitize` 的旧点。全仓 `columns_stale` 只有 5 个写入点、**0 个读取点**
（`grep -rn columns_stale`），也就是说这个信号从未被任何取数路径消费。

**判据**：给定一条横跨某列的控制点不变的清除线，`removed_line_pixels > 0` 且
该列在受影响的层位上读数必须变化。反向：把 `_recompose` 里的失效改成空操作 →
读数回到 13.5714（红）。

**修法（已实现）**：`_recompose` 末尾调 `_invalidate_digitized_points(roi_id)` —— 作废本 ROI
的 `column_points` **与** `control_points`（算法拐点）。只清前者不够：重建会走"从锚点插值"
那条路，用的还是旧掩膜下的拐点。用户手点的锚点存在 `_manual_store()`，`digitize` 重建后
原样并回，不会被丢。重建点在读取侧：`_fill_missing_column_points()` 改成**缺哪列补哪列**
（原型是"整张表为空才补"，所以清掉一列永远不触发重建），导出与 QA 共用。

**不要**改成"静默复用旧点 + 告警"——那正是当前行为。代价：一段 1 万像素级掩膜变更后，
下一次导出会重跑该 ROI 的数字化（本图 19 列 × 1521 行，实测 < 2s）。

### 影响面（S2）

- 子症状 A 影响**所有扫描件**：`resolve_width_max` 的下限 3px 与真实区带线 4–6px 正面对撞，
  小 ROI 图（长边 < 2667px）尤其容易把真线判成"太厚"。判据是纯形状的，不依赖具体图。
- 子症状 B 影响**每一条清理动作**：确认干扰线 / 加排除区 / 刷笔迹之后，导出与 QA 都停在
  `core.digitize` 那一刻的旧点。表现为"清理了但数据没变"，且 `cleanup_stats` 显示已删像素
  （所以用户会怀疑工具而不是怀疑缓存）。
- 修复后代价：掩膜变更后的第一次导出/QA 重跑该 ROI 数字化（现场图 19 列 × 1521 行 < 2s）。

**与 S3 第三条的关系**：用户说"轮廓线会把内部清理过的横线误识别"——因为上面这条
缓存不失效，用户清完线看到的**表**还是带线的旧读数；同时画布的稠密曲线按新掩膜
重画了，两边因此不一致。这类"清理后仍有一行满量程"的层位在归档表里可见：
第 179 行（depth 10.227）7 个窄列同时满格（`s2-line-1667.png`）。

## 4. S3 轮廓线一编辑就退回拐点

### 复现

```python
res = s.digitize(0, "area")                 # 1521 个逐行点（稠密轮廓）
ctrl = [{"row": p["y"], "x": p["x"]} for p in res["control_points"]]   # 436 个锚点
s.set_control_points(0, ctrl)               # 画布每次拖动/微调/删除都会发这个
# → column_points[0] 仍是 1521 行，但形状已被 436 锚点的分段线性插值替换
```

| 量 | 值 |
|:--|:--|
| 稠密轮廓点数 | 1521（每行一个） |
| 锚点数（自动拐点） | 436 |
| 写回后 mean\|Δx\| | **0.681 px** |
| 写回后 max\|Δx\| | **47.0 px** |
| 未被改写的行 | 只有锚点所在行（Δ=0） |

47px 在 Picea（60px 满量程）上是 11 个百分点的位移 —— 用户看到的就是"轮廓线
一编辑，整列弹回折线"。

### 根因

- `digitize.py:643` `set_control_points` 的契约是**整列替换**（"points 语义是
  「这一列现在就是这些锚点」"），`digitize.py:687` 写 `control_points` 后调
  `update_control_point` 重建整列。
- 前端 `GeologyCanvas.ts:1413` `commitControlPoints` 把 `col.controlPoints`
  （镜像里的**锚点**，不是稠密曲线）整列推给后端，并 `col.curvePoints = undefined`
  让画布按锚点折线重画。`main.ts:235` 是唯一出口。

所以"编辑一个点"与"用 436 个锚点重画整列"在实现上是同一个动作，**密度信息在
第一次编辑时就被丢掉了**，不是渲染问题。

### 判据

> 编辑某一列的 1 个锚点后，与该锚点行距 > k（建议 k=25 行）的行，读数变化必须
> ≤ 1px。当前实现：全列 mean 0.681px / max 47px，锚点之间逐行都变。
> 反向：把 `set_control_points` 换成"只改目标行、其余保持稠密点"的局部补丁 →
> 该判据绿，且锚点所在行的 Δ 仍为用户拖动的量。

### 修法与取舍

- 方向 A（局部补丁）：编辑只改"锚点邻域窗口内的稠密点"，窗口外保留墨迹曲线。
  改动小，但窗口边界会出现折角；需要把 `curvePoints` 的失效范围从"整列"缩到"窗口"。
- 方向 B（偏移量模型）：把手工锚点存成"对墨迹曲线的修正量"，导出时
  `x(row) = ink(row) + correction(row)`。语义最诚实（用户改的是"这条线该在哪"），
  但要动 `column_points` 的唯一语义、导出、画布三处，属于结构性改动。
- **本报告不动代码**：S3 的修复与 S2-B 的缓存失效强耦合（缓存失效后，重建必须
  区分"墨迹稠密点"与"锚点插值点"，否则 A/B 两方向都会在重建时丢用户编辑），
  建议与 S2-B 同一个 PR 落，本报告只出 issue。

### 影响面

`set_control_points` / `update_control_point` 是步骤 7 唯一的手工编辑入口；
凡"先按轮廓数字化、再修几个点"的用户工作流，第一次编辑后就退回拐点密度。
这解释了用户"拐点在大列表现尚好、小列不如轮廓线"：大列拐点间距 vs 曲线细结构
的差在小列上被 0.238/px 放大。

## 5. S4 共识层位只能出 100 多个点，钻孔实际 600+

### 事实

| 量 | 值 |
|:--|:--|
| 归档 `samples` | 203，`source` 全 `auto`，行距 4..11px（中位 8） |
| 当前 main 跑 `extract_horizon_consensus` | **355** 点，行距恒定 4px |
| 600 样所需的行距（ROI 高 1516px） | **2.53px** |
| 步骤 7 可用的层位来源 | 共识提取 / 粘贴深度 / 手工加点（`samples.py:104`、`:133`、`samples_set`） |
| 等距网格能力 | 后端有：`export.py:1509` `apply_depth_grid` + `core.extractGridValues`；**前端 0 调用点**，只在导出面板作为 `dataset=depth_grid` 的一个下拉项出现 |

`extract_horizon_consensus`（`core.py:1928`）的算法是「每列 `find_peaks(prominence=
ptp×0.04, distance=3)` 取峰谷 → 按 `tolerance_px=2.5` 聚类」，**点密度 = 拐点数，
与被测样品的真实采样间隔无关**。归档 203 vs 现在 355 的差异本身就是证据：同一张图、
同一算法，只因数字化从「稀疏控制点」变成「稠密逐行曲线」（`e91f721`），拐点数就翻了
75% —— 也就是说这个数**不稳定，不能当"样点密度"用**。

### 复现

```python
s.samples_extract_consensus()            # → 355 个层位（归档里是 203 个，同一张图）
s.apply_depth_grid(start_depth=2.0, end_depth=5.0, step=0.01)   # 只有导出侧能调通
s.samples                                # 仍然是共识那 355 个 —— 网格没进层位
# 前端：grep -rn "applyDepthGrid" frontend/src  → 只有 types/rpc.ts 的方法名，0 个调用点
```

### 判据

> 给定 `step`（深度单位）与 ROI 深度区间，步骤 7 应能一次生成
> `floor((end−start)/step)+1` 个层位，且 `samples` 的 `row_px` 严格递增、
> 行距恒定（±0.5px）、全部落在 ROI 的 y 范围内。
> 本图 `step = 0.02 ka` → 应有 ≥ 600 行；实现后实测行距应等于
> `step / 0.00765 = 2.61px`。
> 反向：把网格来源实现成"取共识点再等分" → 行距不恒定（4..11px），判据红。

### 修法（已实现，`samples.fromDepthGrid`）

复用同一套 `y_scale` 换算，**不新造采样器**：`step/start/end` → 深度序列 → 整数行 →
写进 `samples`（默认导出行集）与 `depth_grid`（`dataset=depth_grid`）同一批数。

**本工程实测能力上限**（0.00765 ka/px，标定段 y 592..984 共 392px）：

| step | 层数 | 行距 | 备注 |
|:--|:--|:--|:--|
| 0.02 ka | 151 | 3px | |
| 0.01 ka | 301 | 1px | |
| 0.008 ka | 376 | 1px | |
| 0.005 ka | — | — | 报错：601 个深度会落到 393 行上 |

⇒ **本工程 600+ 层不可达**：标定段只有 392px，物理上限 393 层。要 600 层必须让
`depth_calibration` 覆盖整个 ROI（316..1836），那是相邻发现 1 的修复，不是采样器的问题。
实现里对这种情况**报错并给出该图分辨率**，不静默去重、不外推。

- 取舍：网格层位与共识层位是**两种行集**，不能混。步骤 7 现在把 `grid` 作为
  `samples.source` 的第四个合法取值显示出来（列表统计 Auto/Paste/Manual/Grid 分列）。
- 外推拦截：区间默认取 `ROI 深度范围 ∩ 标定区间`，显式越界即 `INVALID_PARAMS`，
  所以"按 ROI 外推出一批假年龄"这条路已经被堵住。

### 影响面（S4）

- 只新增一种行集来源，不改共识/粘贴/手工三条既有路径；`samples.set` 仅多认一个合法取值
  `grid`（未知取值仍落 `manual`，既有行为不变）。
- `depth_grid` 与 `samples` 从此同源写：`dataset=depth_grid` 的导出行位与默认导出一致，
  不再出现"面板选网格 / 默认导出"两套行位。
- 工程包 schema 不变（`depth_grid` 本来就在 v3.0 schema 里，含持久化与载入测试）。

## 6. S5 表与图不对应：两个独立机制

### 6.1 机制 A（硬 bug）：工程包里的 `plot_strat.R` 不看列量纲

归档 `plot_strat.R` 全文 6 行，最后一行：

```r
strat.plot(df[-1], yvar=df[[1]], y.rev=TRUE, scale.percent=TRUE, plot.line=TRUE,
```

与 `project.py` 保存工程包时**硬编码**的字节串逐字符相同（406 B），而导出数据 tar 走

判据：工程包里的 `plot_strat.R` 必须与导出数据 tar 里的同名脚本**同一生成器**
（本报告已出的 PR 就是把生成器抽到 `export_docs.strat_plot_script_lines`，两处共用）。
反向：把 `_plot_strat_script_for_csv` 换回硬编码 → `strat.plot(` 计数 2→1，判据红。

### 影响面（S5）

- 机制 A 只影响"保存工程包"这一条通道（`data.csv` / `straditize.json` / 图像字节都不变，

### 6.2 机制 B（观感，不是 bug）：画布画稠密曲线，表只有 203 行

## 7. 未定性与缺什么证据

0. **S1 本轮没有改代码，原因写在证据里**：试过两族"自动量轴粗"的判据
   （① 灰度层种子改到 ±2px 内最暗列；② 近黑 + 通高的绝对判据），在
   `.recon_20261117` 与 hoya 基线上都出现过度/欠检测（同一张图 19 列里 8 列正确、
   11 列给出 0 或明显偏大）。**判据本身没有判别力，所以不推代码**，只推测量证据
   （本报告 §2 + issue `#46`）。可用的下一步见 §2「修法」第一条（把
   "实测轴粗 ≠ 生效轴粗"作为提示报出来），它需要的正是一个可靠的自动测量。
1. **S1 的"正确 0 点"到底是轴芯中心还是轴线右缘**：本报告用「曲线静止位」
   （`start+5`）作为可比参照，判据只主张"当前 0 点比静止位左移 4px"，不主张
   "右缘就是物理学上的 0"。要定死需要**图上的刻度齿/标尺原图**（本工程
   `tickEndX` 全写成 `start+2`，无可信标尺）。取法：向用户要该图的原始出版物或
   图上刻度标签的高分辨率截图。
2. **S2-A 的线宽分布**：本报告只量了这一张图的 4 条线（3px/4px×3）。要定
   `_AUTO_WIDTH_RATIO` 的新取值，需要 `tests/data/figures/` 下 ≥3 张真实扫描件的
   厚度直方图（本报告建议的"直方图证据"就是为此）。
3. **S3 方向 B（偏移量模型）的可行性**：未验证"锚点修正量"与 `extract_horizon_consensus`
   的拐点语义会不会打架（拐点是"取点"，修正是"位移"）。缺一次对
   `docs/ARCHITECTURE.md §6.4` 口径的评审。
4. **S4 的 `step` 语义**：用户说"600+ 样品"指**采样间隔**还是**图上可分辨行数**
   （1516px 的图在 2.53px 间距下已经接近抗锯齿极限）。缺用户的真实采样间隔
   （cm 或 ka）。
5. **UI 层未截屏**：本报告所有证据来自像素与后端返回值。`pixi run app` 在本机
   8765 端口被占时未能启动，未做 UI 复现。缺：一次干净的 UI 现场（同一工程点
   步骤 4「检测干扰线」、步骤 7「提取共识」、步骤 8「保存工程包」各一张截图）。
