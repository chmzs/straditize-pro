## 2. S1 小列偏位：读到的是**夸大线**（×5），不是 0 点偏移

> **结论更正（2026-11-17 真机 + 逐行测量）**：本节早先写成"0 点比墨迹静止位左移 4px"，
> 那是**次要项**（只值 ±0.95%）。主因是这四列画了**两层曲线**，而导出取"最右墨迹"，
> 正好取到放大后的那条。

### 复现

```python
s = load()                                   # 见 §1（load_image + project_load）
s.digitize(0, "area")                        # Picea：1521 个逐行点
payload["columns"][0]["tickValue"]           # 0.2381 %/px —— 由图上刻度（放大后）标定
# 导出：Picea 中位 4.286%、最大 13.57%
# 真实值（内线，逐行实测）：中位 1.190%、最大 3.571%
```

### 数据证据（1520 行/列，`assets/recon-20261117/s1-two-layer-rows.csv`）

| 列 | 外线/内线 比值 中位（p25–p75） | 现导出 p50 | 真实值 p50 |
|:--|:--|--:|--:|
| Picea | 4.50（4.0–5.0） | 4.286% | 1.190% |
| Pinus | 3.75（3.4–4.1） | 5.714% | 1.905% |
| Betula | 4.42（4.1–4.7） | 8.095% | 1.905% |
| Quercus | 4.00（3.3–4.8） | 2.381% | 0.952% |

- 合并比值 **4.17**（p5–p95 = 3.00–5.25，93.5% 落在 [3.0,5.5]）；4–6 / 7–9 / 10–14px
  三档中位 4.17/4.14/4.20 ⇒ **纯乘性，无加性偏移**。
- 与论文标注的 **5×** 差 ~17%，属描边宽度与像素量化误差 —— 倍率以论文为准，由用户填入。
- 归零证据：17 个 % 列的总和中位 **122.4%**（物理上不可能）→ 按 5× 除回来 **108.6%**，
  且最低层位落在 99.8%。再扣掉 4px 常数底（17 列 × 0.95 ≈ 16 点）≈ 93%，差额与图上
  未数字化的类群一致。
- 判据：图上一个 17 类孢粉的百分比图，任一层位的总和必须 ≤ 100%（含容差）。

### 根因（三层，按贡献排序）

1. **取数口径（主因）**：`digitize` 取"本列该行最右墨迹"，在"两层曲线"的列上等于取外线
   （夸大值）；而斜率是按图上刻度（放大后的量程）标的，于是导出=夸大值。落点
   `session_parts/digitize.py` 的 `_read_column_profile`（面积读法）。
2. **倍率在解析链上被丢弃（放大器）**：`xscale._scale_from_group_slope` 用
   `exaggeration_mult=_group.get(...)` 覆盖了已经解析好的形参 ⇒ 组斜率路径（真实工程正是
   这条，`source="group_slope"`）下令牌级倍率完全无效、`px_to_value` 从不做除法。
3. **外线在部分行整根缺失（噪声源）**：实测这些行"外线应在位置"灰度 p10/p50/p90 =
   255/255/255（100% 纯白，Picea 229 行 / Pinus 221 / Betula 58 / Quercus 484）⇒ 外线是真没画，
   不是浅。这些行读到内线，再 ÷5 就把值压小 5 倍 → 假低谷（跳变 p50 1.25–3.33 个百分点）。
4. **次要项：0 点 4px 常数底**：`measure_axis_stroke` 在抗锯齿左缘上把轴粗量成 1px
   （实测轴芯 5px），0 点比静止位左移 4px ⇒ 每列 +0.95%。÷5 后这四列只带 +0.19%，
   其余 13 列仍 +0.95%。详见 #46 的次要项。

### 修法（已实现）

| PR | 内容 |
|:--|:--|
| `#55` | 外线断开行按「内线 × 倍率」补回（带 4px 可分辨性下界，小值行判不出就不动、只标 `ambiguous`）；修第 2 条的形参覆盖 bug |
| `#56` | 侧栏"峰值（实测最大）"除以倍率（真机 13.6% → 2.7%，与导出表一致） |
| `#57` | 量化取证（6080 行明细 + 两张放大图 + 方法与阈值敏感性） |

**弃用"读内线"这条路**：内线只有 4–8px 宽，1px = 0.238%，读它的量化噪声是"外线÷倍率"的
4.5 倍；且 Quercus 只有 14.7% 的行能把两层分开。分支 `feat/reader-area-exaggerated` 不合，
其中"四分分类"的判据已以更小的形式并入 `#55`。

### 影响面

- 影响**所有把数据放大画出来的列**（本图四列：Picea/Pinus/Betula/Quercus），偏差 3.75–4.50 倍；
  未放大的列不受影响。
- 三个出口本来就不一致：导出/QA 已是真值（÷倍率），侧栏显示夸大值（`#56` 修）；
  用户"设了倍率没反应"的观感来自第 2 条 bug + 侧栏不跟着变。
- 倍率是**论文给出的元数据**（常见 5× 或 3×），由用户在列/组上填，不做图像自动估计。

## 3. S2 横线检测只到一条；手动清除线无效

### 3.1 子症状 A：4 条真区带线只检出 1 条

**复现**

```python
s.detect_line_candidates(roi_id="roi_1")   # → 1 条（y=671, 3px, Kind A）
```

ROI 行覆盖率（`foreground` 在该行的占比）实测：

| 行 | 覆盖率 | 厚度 | 结果 |
|:--|:--|:--|:--|
| 670–672 | 0.816–0.845 | 3px | **检出** |
| 1039–1042 | 0.999–1.000 | **4px** | 拒（`width > max_width`） |
| 1296–1299 | 0.800–0.833 | **4px** | 拒 |
| 1666–1669 | 0.977–0.982 | **4px** | 拒 |

**根因**：`lines.py:26` `_AUTO_WIDTH_RATIO = 0.0015`，`resolve_width_max`
（`lines.py:68`）= `max(3, round(2096×0.0015)) = max(3, 3) = 3`；`_projection_line_rows`
（`lines.py:86`）用 `len(chunk) <= max_width` 过滤 cluster。这张图的区带线是 4px，
**差 1 像素，三条真线全被当"太厚"扔掉**。

**判据**：同一 ROI 下，`detect_line_candidates` 必须返回 y≈671 / 1040 / 1297 / 1667
四组 Kind A；且 1105 行「0.30<覆盖率≤0.75」的行里不得新增候选（防"放宽阈值换召回、
顺手把曲线当线"）。反向：把比值调回 0.0015 → 计数 4→1。

**修法与取舍**：比值是**经验标定**（注释里写明 6px/4855px），但下限 `max(3, …)` 把
小 ROI 图的容差压到 3px，恰好卡在真实扫描件的 4px 线宽上。建议改成
`max_width = max(3, round(long_side × ratio))` **+ 一个显式的"厚度直方图"证据**：
先算 `line_width_min..8` 各厚度上的候选数，若某厚度上有一簇（≥3 条）且与
`max_width` 只差 1–2px，就把 `max_width` 抬到该簇上限，并在响应里带
`width_max_used` 与 `width_histogram`。不做无限放宽 —— 那会把列内曲线纹理当线。

### 3.2 子症状 B：手动添加的清除横线对导出无效（掩膜变了，表没变）

**复现**

```python
for c in s.columns: s.digitize(c["col_index"], "area")   # 用户此时已数字化
before = export_picea(depth=10.227)      # 13.5714
s.upsert_line_geometry(roi_id="roi_1",
                       geometry={"x0":939,"y0":1664,"x1":3030,"y1":1671},
                       axis="h", selected=True)
# → stats.removed_line_pixels = 11335（掩膜确实改了）
after  = export_picea(depth=10.227)      # 13.5714  ← 一字未变
s.rois[0]["columns_stale"]            # True
```

同时验证：**重新 `digitize` 之后**，同一行 Picea 从 997 → 939（落回 0 点），
y=1675 从 966 → 947 —— 说明几何与掩膜链路本身是对的，坏在"取数缓存不失效"。

**根因**：`cleanup.py:886` 在 `_recompose` 末尾只置 `roi["columns_stale"] = True`，
而 `column_points`（导出唯一读取的逐行点集）没有失效点；`export.py:1304`
`_ensure_export_column_points` 只在 `column_points` **为空**时补点，于是导出读到的是
上一次 `core.digitize` 的旧点。全仓 `columns_stale` 只有 5 个写入点、**0 个读取点**
（`grep -rn columns_stale`），也就是说这个信号从未被任何取数路径消费。

**判据**：给定一条横跨某列的控制点不变的清除线，`removed_line_pixels > 0` 且
该列在受影响的层位上读数必须变化。反向：把 `_recompose` 里的失效改成空操作 →
读数回到 13.5714（红）。

**修法（已实现）**：`_recompose` 末尾调 `_invalidate_digitized_points(roi_id)` —— 作废本 ROI
的 `column_points` **与** `control_points`（算法拐点）。只清前者不够：重建会走"从锚点插值"
那条路，用的还是旧掩膜下的拐点。用户手点的锚点存在 `_manual_store()`，`digitize` 重建后
原样并回，不会被丢。重建点在读取侧：`_fill_missing_column_points()` 改成**缺哪列补哪列**
（原型是"整张表为空才补"，所以清掉一列永远不触发重建），导出与 QA 共用。

**不要**改成"静默复用旧点 + 告警"——那正是当前行为。代价：一段 1 万像素级掩膜变更后，
下一次导出会重跑该 ROI 的数字化（本图 19 列 × 1521 行，实测 < 2s）。

### 影响面（S2）

- 子症状 A 影响**所有扫描件**：`resolve_width_max` 的下限 3px 与真实区带线 4–6px 正面对撞，
  小 ROI 图（长边 < 2667px）尤其容易把真线判成"太厚"。判据是纯形状的，不依赖具体图。
- 子症状 B 影响**每一条清理动作**：确认干扰线 / 加排除区 / 刷笔迹之后，导出与 QA 都停在
  `core.digitize` 那一刻的旧点。表现为"清理了但数据没变"，且 `cleanup_stats` 显示已删像素
  （所以用户会怀疑工具而不是怀疑缓存）。
- 修复后代价：掩膜变更后的第一次导出/QA 重跑该 ROI 数字化（现场图 19 列 × 1521 行 < 2s）。

**与 S3 第三条的关系**：用户说"轮廓线会把内部清理过的横线误识别"——因为上面这条
缓存不失效，用户清完线看到的**表**还是带线的旧读数；同时画布的稠密曲线按新掩膜
重画了，两边因此不一致。这类"清理后仍有一行满量程"的层位在归档表里可见：
第 179 行（depth 10.227）7 个窄列同时满格（`s2-line-1667.png`）。

## 4. S3 轮廓线一编辑就退回拐点

### 复现

```python
res = s.digitize(0, "area")                 # 1521 个逐行点（稠密轮廓）
ctrl = [{"row": p["y"], "x": p["x"]} for p in res["control_points"]]   # 436 个锚点
s.set_control_points(0, ctrl)               # 画布每次拖动/微调/删除都会发这个
# → column_points[0] 仍是 1521 行，但形状已被 436 锚点的分段线性插值替换
```

| 量 | 值 |
|:--|:--|
| 稠密轮廓点数 | 1521（每行一个） |
| 锚点数（自动拐点） | 436 |
| 写回后 mean\|Δx\| | **0.681 px** |
| 写回后 max\|Δx\| | **47.0 px** |
| 未被改写的行 | 只有锚点所在行（Δ=0） |

47px 在 Picea（60px 满量程）上是 11 个百分点的位移 —— 用户看到的就是"轮廓线
一编辑，整列弹回折线"。

### 根因

- `digitize.py:643` `set_control_points` 的契约是**整列替换**（"points 语义是
  「这一列现在就是这些锚点」"），`digitize.py:687` 写 `control_points` 后调
  `update_control_point` 重建整列。
- 前端 `GeologyCanvas.ts:1413` `commitControlPoints` 把 `col.controlPoints`
  （镜像里的**锚点**，不是稠密曲线）整列推给后端，并 `col.curvePoints = undefined`
  让画布按锚点折线重画。`main.ts:235` 是唯一出口。

所以"编辑一个点"与"用 436 个锚点重画整列"在实现上是同一个动作，**密度信息在
第一次编辑时就被丢掉了**，不是渲染问题。

### 判据

> 编辑某一列的 1 个锚点后，与该锚点行距 > k（建议 k=25 行）的行，读数变化必须
> ≤ 1px。当前实现：全列 mean 0.681px / max 47px，锚点之间逐行都变。
> 反向：把 `set_control_points` 换成"只改目标行、其余保持稠密点"的局部补丁 →
> 该判据绿，且锚点所在行的 Δ 仍为用户拖动的量。

### 修法与取舍

- 方向 A（局部补丁）：编辑只改"锚点邻域窗口内的稠密点"，窗口外保留墨迹曲线。
  改动小，但窗口边界会出现折角；需要把 `curvePoints` 的失效范围从"整列"缩到"窗口"。
- 方向 B（偏移量模型）：把手工锚点存成"对墨迹曲线的修正量"，导出时
  `x(row) = ink(row) + correction(row)`。语义最诚实（用户改的是"这条线该在哪"），
  但要动 `column_points` 的唯一语义、导出、画布三处，属于结构性改动。
- **本报告不动代码**：S3 的修复与 S2-B 的缓存失效强耦合（缓存失效后，重建必须

## 5. S4 共识层位只能出 100 多个点，钻孔实际 600+

**真机结论（2026-11-17 补测，优先于下面的算法推断）**：这不是"算法做不到"，而是**前端把
合并半径写死成 4.0px**。同一台机器、同一个会话、同一张图，只改 `tolerance_px`：

| `tolerance_px` | 层位数 | 来源 |
|:--|:--|:--|
| 1.0 | **642** | 手工调 |
| 1.5 | 526 | 手工调 |
| 2.0 | 377 | 手工调 |
| 2.5 | 355 | 后端默认（`samples_extract_consensus` 形参默认值） |
| 3.0 | 293 | 手工调 |
| **4.0** | **207** | **UI 实际发的值**（`frontend/src/services/InspectorBridge.ts:515`） |
| 6.0 | 136 | 手工调 |

用户在 UI 上点「提取采样共识层位」得到 207 层（`ui-step7-consensus-207.png`），而钻孔实际
600+ 样品 —— **数量上今天就能到 642，卡在 `tolerance_px: 4.0` 这个硬编码常量上**。
642 是否就是真实样品层，需要用户按自己的采样方案判定（本文只主张"数量可达"，不主张
"这 642 行就是样品"`#待处理/需用户确认`）。

### 事实与复现（真机）

```js
// 页面内直接打 RPC（同一会话、同一张图）
samples.extractConsensus {}                                  // → 355（后端默认 2.5）
samples.extractConsensus {tolerance_px: 4.0, min_taxa_support: 1}  // → 207（= UI 按钮）
samples.extractConsensus {tolerance_px: 1.0, min_taxa_support: 1}  // → 642
```

UI 路径：`.recon_20261117` 载入 → 步骤 7 →「提取采样共识层位」→ 层位列表 207 层。
代码落点：`frontend/src/services/InspectorBridge.ts:515`
`samples.extractConsensus', { tolerance_px: 4.0, min_taxa_support: 1 }`。

### 次因：步骤 7 没有等距网格入口

| 量 | 值 |
|:--|:--|
| 归档 `samples` | 203（`source` 全 `auto`），行距 4..11px（中位 8） |
| 步骤 7 的来源 | 共识提取 / 粘贴深度 / 手工加点（`samples.py:104`、`:133`） |
| 等距网格能力 | 后端有 `export.py:1509` `apply_depth_grid` + `core.extractGridValues`；**前端 0 调用点**（只在导出面板作为 `dataset=depth_grid` 的下拉项） |

`extract_horizon_consensus`（`core.py:1928`）的算法是「每列 `find_peaks(prominence=
ptp×0.04, distance=3)` 取峰谷 → 按 `tolerance_px` 聚类」。所以层位数 = f(拐点数, 合并半径)，
**与真实采样间隔无关**；同一个"600+"既可以由放小合并半径得到，也可以由等距网格得到，
两者语义不同（拐点层位 = 形态突变处；网格层位 = 固定间隔）。

### 判据

- **主因**：同一会话里 `tolerance_px=1.0` 必须给出 ≥600 个层位，`tolerance_px=4.0` 给出
  ≈207，且两者只差这一个参数（已实测：642 / 207）。UI 必须让用户看见并调整这个参数，
  或给出与真实采样间隔一致的默认值。
- **次因（网格）**：给定 `step` 与区间，一次生成 `floor((end−start)/step)+1` 个层位，
  `row_px` 严格递增、行距恒定（±0.5px）、全部落在 ROI 内。
  本图 `step = 0.02 ka` ⇒ 151 层（行距 3px）；`0.01 ka` ⇒ 301 层（1px）。
  反向：把网格实现成"取共识点再等分"→ 行距不恒定（4..11px），判据红。

### 修法

- **主因（必做，5 行改动）**：把 `tolerance_px` 从 `InspectorBridge` 的硬编码常量提到步骤 7
  的输入（默认保留 2.5 = 后端口径，或按 `深度分辨率` 推一个默认值），并在按钮旁显示
  "当前合并半径 → 预计层位数"。—— 这是 S4 用户抱怨的直接解。
- **次因（PR #52 已实现）**：`samples.fromDepthGrid` 提供等距网格行集，与共识行集并列，
  不能互相冒充。

### 影响面（S4）

- 只新增一种行集来源，不改共识/粘贴/手工三条既有路径；`samples.set` 仅多认一个合法取值
  `grid`（未知取值仍落 `manual`，既有行为不变）。
- `depth_grid` 与 `samples` 从此同源写：`dataset=depth_grid` 的导出行位与默认导出一致。
- 工程包 schema 不变（`depth_grid` 本来就在 v3.0 schema 里）。

### 顺带必须报的既有缺陷

本工程 `depth_calibration` 只覆盖 y 592..984（2.0–5.0 ka），而 ROI 是 y 316..1836，
导出深度因此**外推**到 −0.06..11.49 ka；等距网格在标定段内的物理上限是 392 层
（0.00765 ka/px），600 层需要标定覆盖整个 ROI。实现里对"步长细于行分辨率"直接报错，
不外推（`ui-step7-consensus-207.png` 右侧显示 `深度分辨率: 0.008 ka/px`）。

## 6. S5 表与图不对应：两个独立机制

### 6.1 机制 A（硬 bug）：三处生成的 `plot_strat.R` 互不相同，只有归档那条按量纲

## 7. 未定性与缺什么证据

0. **S1 本轮没有改代码，原因写在证据里**：试过两族"自动量轴粗"的判据
