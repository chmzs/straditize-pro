# 刻度齿判据 —— 已放弃"齿数真值"，改用结构性判据

> **状态：本文件 v1 给出的"89 齿"已自我废弃。**
> 旧版留档于 [`xticks-ground-truth-ARCHIVED-v1.md`](./xticks-ground-truth-ARCHIVED-v1.md)，
> 仅供追溯"为什么这条路走不通"。
>
> **原因**：齿数对判据参数高度敏感，六次测量得到六个不同数字
> （46 / 49 / 110 / 89 / 169 / 66）。它不是可复现的量，**不可作验收真值**。
>
> **现行判据**：band 定位 + 可用列数 + 双向零回归。见 §2。

## 0. 一句话结论

**不要再数齿。** 用两条结构性判据：

1. **band 必须落在 `y ∈ [868, 878]`**（物理结构：横轴 869 + 齿 870–875）
2. **可用列数 ≥ 总列数 90%**（真齿区实测 12/12，数字区 2/12）

两条都不依赖齿数、不需要真值，且经 30 组参数扫描证明稳健（§3）。

## 1. 六个数字的成因（全部实测复现）

| 数字 | 出处 | 成因 | 错在哪 |
| -: | :--- | :--- | :--- |
| **46** | `scripts/prod_gate/g01_xticks_probe.py` `truth_ticks()` | `a[871:876]` 5 行全暗 + 合并≤2px + 限 `[330,1290]` | **含 16 个列框线**（缺 T2） |
| **49** | Lead，阈值 `dark<110` | 同上，未排除框线 | 含框线污染 |
| **110** | backend-fixer "候选群" | 判据未记录，推测更宽 | 不可复现 |
| **89** | 本文件 v1（`DARK=160`, 齿长 `[3,8]`, 取 `axis_rows[-1]`） | **某组参数下的测量值** | 把它当真值是错的 |
| **169** | Lead 逐字复现 v1 | **对 `y=232` 与 `y=869` 两条整行级轴线都数了齿**：80 + 89 = 169 | `y=232` 是数据区**顶边框**，不是刻度尺 |
| **66** | Lead，同参数 | 未做"合并相邻 ≤2px"，一根齿被数成多根 | 口径不一致 |

### 1.1 169 的成因（最有价值的一条）

```
y=232 齿=80  +  y=869 齿=89  =  169
```

`y=232` 暗占比 55%（超过"整行级轴线"阈值 50%），但它是**数据区顶边框**。
顶部框线下方也有短竖线（各列框线的上端），所以能凑出 80 个"齿"。

**教训**：`find_axis_rows` 返回多个候选时，**必须先确定哪一条是刻度尺**
（刻度尺在数据区底缘 → 取最后一条），再只数那一条。

### 1.2 89 为什么不是真值

同一判据结构，只改参数：

| 变化 | 齿数 |
| :--- | -: |
| 阈值 110 → 180（齿长 `[3,8]` 固定） | 51 → 70（Lead）/ 49 → 79（我） |
| 齿长下限 2 → 4（阈值 160 固定） | 90 → 52（Lead）/ 79 → 62（我） |

**更糟的是方向可能反**：Lead 实测数字区 `band=(886,892)` 总齿 **55** >
真齿区 `(870,876)` 的 **51**。**齿数连"对/错"的方向都指示不了。**

## 2. 现行判据（结构性，不需要真值）

### 2.1 判据 A：band 落在物理齿区

| 项 | 内容 |
| :--- | :--- |
| **要求** | 产品自动搜索出的 band 起点 `∈ [868, 878]` |
| **物理依据** | `y=869` 横轴线，`y=870..875` 真齿，`y≈883+` 印刷数字 |
| **挡住** | ① band 落数字区（`y≥883`；Lead 实测到 backend-fixer 选中 `[886,892]`）② band 落顶部框线（`y=232`） |

```
  y=869:  ###########            <- 横轴线
  y=870:  .......#...            <- 真齿（从轴线向下伸出）
  y=871:  .......#...
  y=872:  .......#...
  y=873:  .......#...
  y=874:  ...........            <- 齿结束
  y=883+: 数字（0/5 字形）
```

### 2.2 判据 B：可用列数（关键结构性判据）

| 项 | 内容 |
| :--- | :--- |
| **定义** | 一列"可用" = 其像素范围内至少匹配到 **2 个刻度齿**（两点式标定所需端点） |
| **要求** | 可用列数 ≥ 总列数 × 90% |
| **为什么稳健** | 它问的不是"数到几个"，而是「**每列是否都找到了属于自己的一对端点**」——这正是"自动提取刻度"功能的定义 |
| **为什么能区分** | 真齿在每列下方都有；数字笔画只在碰巧有数字处才有 |

**独立复验（我实测，数值与 Lead 不同但结论一致）**：

```
band=(870,876)  真齿区  总齿= 79  可用列=12/12   ← 正确
band=(870,875)  真齿区  总齿= 79  可用列=12/12
band=(869,875)  含轴线  总齿= 79  可用列=12/12
band=(886,892)  数字区  总齿= 43  可用列= 2/12   ← 错误
band=(880,890)  数字区  总齿= 42  可用列= 2/12
band=(283,295)  数据区  总齿= 17  可用列= 2/12
```

**我的总齿（79/43）与 Lead 的（51/55）不同——又一次证明齿数不可复现。
但可用列 12/12 vs 2/12 完全一致。** 这就是结构性判据与计数量的区别。

### 2.3 判据 C/D：双向零回归

| 判据 | 要求 | 依据 |
| :--- | :--- | :--- |
| **C** | `hoya` = **0** 齿 | 该图无刻度尺；历史缺陷是报 53 个伪齿 |
| **D** | `beginner` = **0** 齿 | 无刻度尺 |

hoya 陷阱（Lead 已确认）：`y=1305..1325` 是图例文字（能看出 "A/C"）。
我实测 hoya 的整行级轴线候选含 `1306/1307, 1312/1313` —— 正是图例区。
故必须取**最后一条**整行级轴线（`y=1375`）。

## 3. 稳健性证明（15 组参数扫描）+ 两条实测边界

`DARK ∈ {110,140,160,180,200}` × `min_rows ∈ {3,4,5}`：

| 指标 | 真齿区 `(870,876)` | 数字区 `(886,892)` |
| :--- | :--- | :--- |
| **总齿数** | **49 – 79**（漂 1.6×） | 37 – 45 |
| **可用列数** | **12/12（恒定）** | **2/12（恒定）** |

15 个组合里可用列数**无一次误判**。总齿数漂 1.6 倍。

### 3.1 边界一：`min_rows=2` 不可用（必须 ≥3）

我第一版扫描包含 `min_rows=2`，结果在 `DARK≥180` 时真齿区可用列**掉到 0/12**。
查因：阈值调大后更多灰像素算暗，`band` 内几乎每列都 ≥2 行暗 ——
相邻列被合并成一根，反而凑不出"每列 2 个齿"。

**故 `min_rows` 下限必须 ≥3。** 这是实测得出的硬约束，不是偏好。

### 3.2 边界二：顶部框线区 —— **作者口径与 Lead 口径结论相反（未定论）**

> **⚠️ 本小节的数字已随列集修正，但两方结论仍不一致，如实并列。**

**列集来源（Lead 提问，此处明确）：**
产品 `detect_columns` 在 ROI `[330,1330] × [233,869]` 上的真实输出，共 **16 列**：
`(332,370) (370,407) (407,444) (444,482) (482,519) (519,582) (582,619) (619,656)
(656,694) (694,906) (906,1093) (1093,1130) (1130,1193) (1193,1231) (1231,1279) (1279,1330)`

`load_image` 的自动建议 ROI 是 `[69,1867] × [266,744]`，**不可**直接用于此处。
（本文件早期版本手挑其中 12 个窄列，漏掉 col15/col16，分母错误；已修正为 16。）

**两方实测（同图、同 DARK=160、同 16 列，仍不一致）：**

| band | 作者测得 | Lead 测得 |
| :--- | :--- | :--- |
| `(232,240)` 顶部框线 | 齿 79 / **可用 16/16** | 齿 2 / **可用 0/16** |
| `(870,876)` 真齿区 | 齿 79 / **16/16** | 齿 51 / **16/16** |
| `(886,892)` 数字区 | 齿 43 / **6/16** | 齿 55 / **6/16** |

**数字区 6/16 双方完全一致**；真齿区可用列也一致（16/16）。
**唯一分歧是顶部框线区（16/16 vs 0/16）。**

**已定位的可能成因：`min_rows`（band 内至少几行暗才算一个"齿列"）**

我实测 `min_rows` 对顶部框线区的结论**完全翻转**：

```
min_rows=1: 齿数= 17  可用列= 1/16
min_rows=2: 齿数= 65  可用列=16/16
min_rows=3: 齿数= 79  可用列=16/16
min_rows=4: 齿数= 79  可用列=16/16
min_rows=5: 齿数= 31  可用列= 9/16
```

`y=232` 下方 `232..239` 八行中，各列框线的**上端**确实有 ≥3 行暗，
故在我的口径（`min_rows>=3`）下被算成"齿"。Lead 的 0/16 应来自更严的判据
（更严的 `min_rows`，或叠加了齿长区间限制）。

**因此"边界二"目前是：作者口径成立、Lead 口径不成立，两方未对齐。**
不影响五条验收的结论（见 §3.2.1）。

#### 3.2.1 为什么这条分歧不影响验收

Lead 的判断正确且更稳健：**"判据 A 与 B 互补"这个结论不依赖边界二的数据**。
理由是双向的：

- 数字区：A ✅ 挡住（不在 [868,878]）**且** B ✅ 挡住（6/16 = 37.5% < 90%）
- 顶部框线：A ✅ 挡住（232 不在 [868,878]）；B 是否有判别力**取决于 min_rows 口径**
- 因此**无论边界二哪一方对，判据 A 都必须保留** —— 它是唯一稳定挡住顶部框线的那条

这正是"互补"的确切含义：不是"每个区各由一条挡"，而是
"**B 的判别力依赖实现细节，A 的判别力是物理的**"。

实测 `band=(232,240)`（数据区顶边框下方）同样是 **12/12 可用列、79 个"齿"**。
原因：`y=232` 下方紧邻各列框线的**上端**，每个列边界处都有一根竖线 ——
每列左右各一，正好凑出 2 个"齿"。

**这意味着判据 A 与判据 B 是互补关系，不是各自挡一类：**

| 错误区 | 判据 A（band 定位） | 判据 B（可用列数） |
| :--- | :--- | :--- |
| 印刷数字区 `(886,892)` | ✅ 挡住（不在 [868,878]） | ✅ 挡住（2/12） |
| 数据区上方 `(283,295)` | ✅ 挡住 | ✅ 挡住（2/12） |
| **顶部框线 `(232,240)`** | ✅ 挡住 | ❌ **挡不住（12/12）** |

**所以两条判据必须同时用。** 单用判据 B 会把顶部框线当刻度尺。

## 4. 给 task-7 的验收（采纳 Lead 的五条）

| # | 判据 | 类型 |
| -: | :--- | :--- |
| 1 | band 自动定位到 `y ∈ [868, 878]` | 物理结构 |
| 2 | 可用列数 ≥ 总列数 **90%** | 结构性，参数不敏感 |
| 3 | `hoya` **0** 齿 | 双向零回归 |
| 4 | `beginner` **0** 齿 | 双向零回归 |
| 5 | 参考输出打印齿数与 band 坐标，**不作门禁** | 供人工判断 |

### 4.1 明确禁止的验收写法

- ❌ "齿数 = 89"或任何具体数字 —— 参数一变就漂（§1.2）
- ❌ **"齿位集合与真值 ±2px 匹配率 ≥95%"** —— **本文件 v1 曾这样建议，现已撤回**：
  真值本身不确定，匹配率再高也只是"与某个采样点吻合"
- ❌ "总齿数越多越好" —— 数字区反而更多（55 > 51）

### 4.2 错误形态与拦截判据

| 错误形态 | 表现 | 被哪条挡住 |
| :--- | :--- | :--- |
| band 落印刷数字区 | `y ≥ 883`（实测 `[886,892]`） | 判据 1 |
| band 落顶部框线 | `y ≈ 232`（**可用列也是 12/12，B 挡不住**） | **仅判据 1** |
| 含列框线 | 齿数虚高（46/49 即此） | 判据 2（框线只在列边缘，凑不满每列 2 个齿） |
| 凑总数 | 总数对但齿位错 | 判据 2 不问总数，凑总数无意义 |

## 5. 方法论记录

### 5.1 我犯的错（承认）

| 错误 | 说明 |
| :--- | :--- |
| **把 89 当真值提交** | 它只是某组参数下的测量值。正确表述是"参考观测值，随参数漂移" |
| **把"两法一致"当独立证据** | **Lead 指出**：M1/M2 共享同一 T2 前提与同一组阈值，一致只是"同一套假设的两个实现"，属**相关证据而非独立证据**。完全接受 |
| **未报告参数敏感性** | 应在首次给出 89 时就附上漂移区间 |

### 5.2 我做对的事（保留）

| 项 | 价值 |
| :--- | :--- |
| 挖出 46/49 含 16 个列框线 | 证明旧判据错；T2（轴线上方不暗）成为硬要求 |
| 指出"16 列"是产品分列数、随 ROI 变 | 修正 task-7 里一处错误并列 |
| 给出 `--dumps` 可目视入口 | 唯一可证伪通道 |
| 复现 169 的成因（`y=232`+`y=869` 双轴线段累加） | 解释 80 的差额来源 |

### 5.3 核心教训

前五次全在"数齿"，第六次（可用列数）跳出了这个框架。

**当同一个量在不同判据下漂移 2 倍以上、且方向都指示不了对错时，
它就不该当门禁——应换结构性判据，而不是继续调参数。**
